# TASK-092 — Сквозной сценарий цепочки Trigger → Skill → Script → Delivery на четырёх триггерах

## Цель

Один проверяемый результат: автоматический сквозной сценарий доказывает, что одна и та же цепочка Trigger → Skill → Script → Delivery исполняется от каждого из четырёх триггеров (Webhook, Cron, function call, сообщение из чата), пишет чекпоинты в PostgreSQL, переживает рестарт Service посреди исполнения и доставляет результат ровно один раз.

## Контекст

- Цепочки — только линейные Trigger → Skill → Script → Delivery (ADR-003), цепочек много, визуального редактора нет. Пакет скрипта: вход `skill-hack.*`, `netrunner.manifest.json` с обязательными `runtime.language`, `runtime.languageVersion`, `runtime.environment`, `runtime.environmentVersion`, `runtime.entrypoint`; исполнение — своим интерпретатором в песочнице Restricted Token + Job Object + Deny-ACL (TASK-023), лимит памяти — настройка пакета.
- Cron — Quartz.NET в той же PostgreSQL (TASK-045); в тесте расписание не ждётся в реальном времени: используется тестовый триггер Quartz/ускоренные часы по контракту TASK-045.
- Delivery в автоматическом сценарии — фейковый канал на границе TASK-002 со счётчиком и журналом доставок; реальные Telegram/Avalonia — TASK-091 и ручная проверка TASK-093. HITL-гейт цепочки (TASK-046) включается в одном из прогонов через фейковую доставку подтверждения.

## Объём работ

- E2E-тесты (to-be-created, `tests/CyberPipe.Tests.E2E/ChainScenarioTests`) на полной композиции TASK-090 и тестовой PostgreSQL+pgvector: реальные определение цепочки (TASK-040), триггеры (TASK-041), валидатор пакета (TASK-042), раннер (TASK-043, интерпретатор тестового языка фикстуры), исполнитель с чекпоинтами (TASK-044), Quartz (TASK-045), фейковые Skill и Delivery по контрактам TASK-002.
- Фикстуры: две разные цепочки одновременно (доказывает «цепочек много» и изоляцию запусков), тестовый пакет `skill-hack.*` с валидным манифестом (все пять полей `runtime.*`) и детерминированным выходом, входные данные для каждого триггера.
- Прогон по каждому триггеру: Webhook (HTTP-вызов тестового хоста), Cron (тестовое срабатывание Quartz), function call (прямой вызов контракта), chat (фейковое сообщение чата) — везде: шаги Skill → Script → Delivery выполнены в порядке ровно по одному разу, результат Delivery равен ожидаемому выходу скрипта, все чекпоинты шагов — в PostgreSQL.
- Рестарт посреди цепочки: Service останавливается после чекпоинта Script и запускается заново на той же БД; запуск завершается шагом Delivery без повторного вызова Skill и Script (счётчики фейков), итоговая доставка — ровно одна.
- HITL-прогон: цепочка с включённым HITL останавливается перед Delivery до решения; после Approve (фейк) — одна доставка; ветка Reject — доставки нет, запуск завершён по политике TASK-046.
- Негативные ветки: пакет с битым манифестом (нет `runtime.entrypoint` / вход не `skill-hack.*`) отклоняется валидатором до запуска скрипта; падение скрипта (ненулевой выход фикстуры) → Delivery не вызван, запуск `Failed`, повтор — только упавший шаг по политике TASK-044; дублирующий триггер с тем же ключом идемпотентности не создаёт второй запуск.

## Результаты

- Набор E2E-тестов цепочки (`tests/CyberPipe.Tests.E2E/ChainScenarioTests.cs`, 11 тестов): 4 триггера, рестарт, HITL (Approve/Reject), 3 негативные ветки; фикстурные цепочки и пакет скрипта (`tests/CyberPipe.Tests.E2E/ChainComposition.cs`).
- Прогоны: `ChainScenario` 11/11 дважды, полный E2E-проект 17/17 дважды (6 Telegram TASK-091 + 11 chains), unit 508 passed / 0 failed / 1 skipped, architecture 12/12, `dotnet build CyberPipe.slnx` без warnings/errors. БД — контейнер `cyberpipe-test-db` (pgvector:pg16, порт 5433), результаты выше — против живой PG.
- Решения фикстур (все в тестовом проекте, продукт не менялся): `CreateAsync` отключает чужие включённые определения (общая БД переживает прогоны; chat-слушатель срабатывает на все подходящие — stale-цепочки давали 4 запуска вместо 1) и гасит нетерминальные запуски убитых прогонов как `CancelledByCrash` (иначе blanket-`RecoverAsync` вечно ждал чужой HITL); рестарт-тесты создают второй хост с `cleanDefinitions: false`. Флаги fail/defer/flaky ставятся после `CreateAsync` (зачистка при создании стирала их до прогона скрипта). Падение скрипта — две фазы: постоянное падение → `Failed` без доставки + `ResumeAsync` терминального запуска no-op; flaky-скрипт (маркер первой попытки) при `MaxAttempts = 2` → повтор только шага Script, Skill не повторяется, прогон доходит до доставки. HITL-решения идут через «рестарт» (пауза → остановка хоста → решение новым хостом на той же БД — штатный путь CLI-рестарта): Approve → ровно одна доставка без повтора Skill/Script; Reject → `Cancelled` по политике TASK-046, доставки нет.
- Найдено (продукт, вне рамок задачи — кандидаты в follow-up): 1) live-Approve при живом конвейере доставляет дважды: `ChainExecutor` читает чекпоинты один раз на входе, после пробуждения по событию проверка шага Delivery идёт по stale-снимку (`src/CyberPipe.Chains/Execution/ChainExecutor.cs`); 2) live-Reject гоняет `Failed` живого пайплайна против `Cancelled` от `RejectAsync` — `OptimisticConcurrencyException` на строке запуска (проявляется под параллельной нагрузкой). E2E обходит обе гонки путём рестарт-решения; живые пути стоит чинить отдельно.

## Критерии приёмки

- [x] Каждый из четырёх триггеров: запуск завершён, порядок и однократность шагов подтверждены счётчиками фейков, чекпоинты всех шагов читаются из тестовой PostgreSQL.
- [x] Две цепочки, запущенные одновременно от разных триггеров, не путают входы/выходы: каждая доставка соответствует своей цепочке.
- [x] Рестарт после Script: Skill и Script повторно не вызваны, Delivery — ровно один раз, запуск `Completed`.
- [x] HITL: без решения Delivery не вызван; Approve → одна доставка; Reject → доставки нет.
- [x] Битый манифест и падающий скрипт: Delivery не вызван, статусы запуска/шагов в PostgreSQL соответствуют политике TASK-044, второй запуск по тому же ключу идемпотентности не создан.
- [x] Весь набор проходит одной командой ниже без сети; реальное время ожидания Cron в тестах не используется.
