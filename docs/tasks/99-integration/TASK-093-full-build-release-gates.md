# TASK-093 — Полная сборка и ворота выпуска: build, тесты, публикация, дымовой прогон

## Цель

Один проверяемый результат: одна команда/конвейер собирает всё решение в Release, прогоняет все уровни тестов и архитектурные запреты, публикует Service, Desktop и CLI и выпускает манифест артефактов с контрольными суммами; выпуск считается готовым только при зелёных воротах, а дымовой прогон чистой установки подтверждает первый запуск.

## Контекст

- Продукт: Service (служба Windows, установка в `Program Files`, работает постоянно) и Desktop (Avalonia, все ОС, закрывается независимо, управляет Service) — разные приложения; CLI — третий артефакт. Фокус ручного тестирования — Windows (Q6, Q24); сборки Desktop под остальные ОС — компиляционная проверка, не ручной прогон.
- Модели не встроены (Q15): в артефактах нет файлов моделей; первый запуск предлагает стандартный мультиязычный эмбеддинг `multilingual-e5-small` для Tier1 (мастер TASK-063, установка TASK-081), каталоги 15 локальных + 8 облачных — JSON (TASK-080) и включаются в публикацию как данные.
- SLO-цифры (Q11) — цели, а не ворота: измеряются и прикладываются к выпуску отчётом, выпуск не блокируют. Ворота блокируют только: ошибки/предупреждения сборки, падающие тесты, нарушенные архитектурные запреты и запрещённый состав артефактов (Guest, DevTools/Git/Build, Hangfire, отдельные базы подсистем, фиксированный брокер, файлы моделей).
- Пароль PostgreSQL и секреты в артефакты и логи сборки не попадают (TASK-003); на чистой установке, если БД не запускается/не подключается, пользователь получает запрос восстановления подключения и пароля (Q21) — проверяется дымовым прогоном.

## Объём работ

- Скрипт выпуска (to-be-created, `eng/release.ps1` и/или одноимённая цель CI — выбор фиксируется при реализации, контракт — команды ниже): последовательные ворота G1–G6, каждое с отдельным статусом в итоговом отчёте; падение ворот останавливает выпуск и называет упавшее ворота и лог.
  - G1 Сборка: `dotnet build CyberPipe.slnx -c Release` без ошибок и предупреждений (`TreatWarningsAsErrors` из TASK-001).
  - G2 Тесты: unit, component, integration, contract, architecture, e2e (включая TASK-091, TASK-092) одной командой `dotnet test CyberPipe.slnx -c Release`; e2e без сети и реальных токенов.
  - G3 Архитектура и запреты: архитектурные тесты TASK-001/TASK-090 + поиск по исходникам и по составу публикаций запрещённых идентификаторов/пакетов (Guest, DevTools/Git/Build, Hangfire, SQLite, конкретные брокеры транспорта, отдельные базы подсистем); проверка, что `CyberPipe.Contracts` не ссылается на проекты решения и пакеты брокеров.
  - G4 Данные выпуска: валидация каталогов моделей JSON (ровно 15 локальных + 8 облачных, схема TASK-080), наличие манифестов фикстурных пакетов `skill-hack.*` только в тестах, отсутствие файлов моделей и секретов в публикациях.
  - G5 Публикация: `dotnet publish` — Service (win-x64, оформление службы — TASK-020), Desktop (win-x64; плюс проверочные сборки linux-x64 и osx-x64 без ручного прогона), CLI (win-x64). Раскладка установки: Service и Desktop — отдельные каталоги/пакеты, установка Service рассчитана на `Program Files`, Desktop ставится и обновляется независимо от Service.
  - G6 Манифест и отчёт: `release-manifest.json` (to-be-created, в каталоге выпуска): версия, коммит, список артефактов с SHA-256 и размерами, статусы ворот G1–G5, отчёт замеров SLO-целей (справочно, не блокирует), список известных ручных проверок со статусом «выполнена/не выполнена».
- Версионирование: единый номер версии решения из одного места (свойство в `Directory.Build.props`/параметр выпуска, to-be-created), одинаковый у Service, Desktop, CLI и в манифесте.
- Дымовой прогон чистой установки (автоматизируемая часть): установка публикаций в чистое тестовое окружение Windows → первый старт Service в ограниченном режиме → мастер первого запуска из Desktop предлагает эмбеддинг `multilingual-e5-small` и настройку БД → после настройки тестовой PostgreSQL Service доходит до статуса «готов» → CLI показывает статус и управляет Service (стоп/старт через TASK-021) → Desktop закрывается, Service продолжает отвечать на статус из CLI.
- Ручной чек-лист Windows (прикладывается к выпуску, не автоматические ворота): реальный Telegram-бот (сценарий TASK-091 на живом боте), HITL-кнопки в Telegram и Avalonia, установка локальной модели Qwen3 через Ollama инструментом TASK-081, голосовой ввод (TASK-052), перезапуск службы Windows из оснастки/Desktop.

## Вне рамок

- Реализация установщика уровня продукта (MSI/магазины ОС), подписывание кода сертификатом издателя, автообновление, CI-инфраструктура организации — задача даёт скрипт выпуска и манифест; боевой CI и подпись — отдельное решение владельца. Исправление бизнес-логики по итогам прогонов — в задачах областей, не здесь.

## Результаты

- Скрипт выпуска с воротами G1–G6, публикации Service/Desktop/CLI, `release-manifest.json`, отчёт замеров SLO, ручной чек-лист Windows.

## Критерии приёмки

- [ ] Одна команда выпуска на чистом клоне проходит G1–G6 и создаёт манифест; намеренно внесённое предупреждение компилятора останавливает выпуск на G1 с указанием ворот.
- [ ] Намеренно сломанный тест любого уровня останавливает выпуск на G2; отчёт называет проект и тест.
- [ ] Добавление запрещённого идентификатора (например, пакета Hangfire или типа Guest) в тестовую ветку останавливает выпуск на G3.
- [ ] Каталог моделей с числом записей, отличным от 15 локальных/8 облачных, останавливает выпуск на G4; файл модели или секрет в каталоге публикации — тоже G4.
- [ ] Артефакты: Service, Desktop (win/linux/osx сборки), CLI опубликованы; версия во всех артефактах и манифесте совпадает; SHA-256 в манифесте сходится с файлами.
- [ ] Дымовой прогон чистой установки: первый запуск доходит до мастера, мастер предлагает `multilingual-e5-small`, после настройки тестовой БД статус «готов», CLI управляет Service при закрытом Desktop.
- [ ] SLO-отчёт приложен и помечен справочным: выпуск с недостигнутой SLO-целью, но зелёными G1–G6 помечается готовым с записью о расхождении, а не блокируется.

## Тестирование

- Уровень: e2e выпуска (build/release gates) + ручной чек-лист Windows.
- Как: ворота G1–G4 — автоматически на чистом клоне; негативные проверки ворот — временными поломками в отдельной ветке/копии, не в основном дереве. Дымовой прогон — чистая тестовая Windows-среда (ВМ или отдельный каталог установки с чистой тестовой PostgreSQL), без реальных секретов; живой Telegram и Ollama/Qwen3 — только ручной чек-лист с фиксацией результата в манифесте выпуска.
