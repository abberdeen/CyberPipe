# 99-integration — Интеграция, сквозные сценарии и ворота выпуска

## Назначение

Финальная сборка CyberPipe (.NET 10) в единое работающее целое: композиционный корень и DI всех подсистем, сквозной сценарий через Telegram, сквозной сценарий цепочки Trigger → Skill → Script → Delivery и ворота полного выпуска. Ни одна задача области не вводит новой бизнес-логики: задачи только соединяют, проверяют и пакуют результаты областей 01–09.

Канон: [DECISIONS.md](../../plans/DECISIONS.md) (Q1–Q24) и [17-adr-mvp.md](../../plans/initial_arch/17-adr-mvp.md) (ADR-001..ADR-008) перекрывают старые тексты планов и архивы (`arch-glm`, `arch-muse`, `arch-wonder`, отдельные базы подсистем, фиксированный брокер, Hangfire, Mini-n8n/DAG/граф, визуальный редактор, Guest, DevTools/Git/Build, фиксированный Volume Clamp, встроенные модели, жёсткий лимит 64 МБ).

## Жёсткие правила области

- Одна PostgreSQL + pgvector на проект; Quartz.NET — в той же PostgreSQL. Отдельных баз и файловых хранилищ подсистем нет; если подключиться/запустить БД не удалось — попросить пользователя восстановить подключение, спросить пароль от БД (Q21).
- Сообщения — только через собственные интерфейсы проекта (TASK-002), конкретный брокер и транспорт по умолчанию не фиксируются; реализация транспорта заменяема конфигурацией без переписывания логики.
- Цепочки — только Trigger → Skill → Script → Delivery, цепочек много, визуального редактора нет. Триггеры: Webhook, Cron, function call, сообщение из чата. Вход пакета — `skill-hack.*`, обязательные поля `netrunner.manifest.json`: `runtime.language`, `runtime.languageVersion`, `runtime.environment`, `runtime.environmentVersion`, `runtime.entrypoint`.
- Service (служба Windows, `Program Files`) и Desktop — разные приложения; Desktop закрывается независимо и управляет Service (старт/стоп/перезапуск). CLI — третий параллельный канал. Avalonia — все ОС, фокус ручного тестирования Windows.
- Маршрутизация 4 яруса: Tier0 regex → Tier1 ONNX-эмбеддинг + семантический кэш → Tier2 лёгкая LLM → Tier3 тяжёлая LLM. TokenBudgetGovernor: по умолчанию $0.50/день, 4000 (soft) / 12000 (hard) токенов, 3 облачных / 5 локальных ходов; всё настраивается.
- Модели не встроены, включая эмбеддинг: первый запуск предлагает стандартный мультиязычный эмбеддинг `multilingual-e5-small` для Tier1; локальные модели ставит/настраивает UI-инструмент (например Qwen3 через Ollama); каталоги — 15 локальных + 8 облачных моделей, JSON.
- Только Owner, Guest нет. DevTools/Git/Build-скиллов нет. Песочница: Restricted Token + Job Object + Deny-ACL, лимит памяти — настройка. Безопасность аудио/контента — эвристическая оценка риска эмбеддингом, не фиксированный Volume Clamp. HITL-подтверждения — Telegram + Avalonia. Brainstem — изолированный worker под надзором.
- SLO-цифры — цели («доска почёта»), а не ворота приёмки: в TASK-093 они только измеряются и публикуются, сбой SLO ворота не закрывает.
- Кода ещё нет (`CyberPipe.slnx` пуст). Все пути проектов и тестов ниже — to-be-created, фиксируются TASK-001; команды `dotnet build/test/publish` — плановые стандартные команды .NET 10.

## Порядок и зависимости

```text
Области 01–09 (TASK-001..TASK-082) ──► TASK-090 ──► TASK-091 ──┐
                                          │         TASK-092 ──┴──► TASK-093
                                          └────────► TASK-092
```

Циклов нет: TASK-090 — единственный потребитель всех областей; TASK-091/TASK-092 зависят от TASK-090 и параллельно друг другу; TASK-093 замыкает область. Детальные зависимости — только ID в файлах задач; интеграционные задачи не создают зависимостей для областей 01–09 (обратных ссылок нет: области работают на своих контрактах и фейках из TASK-002).

## Общие замечания

- В тестах TASK-091/TASK-092 внешние системы заменяются фейками на границах TASK-002 (транспорт Telegram, LLM-провайдеры, Ollama, интерпретаторы скриптов при необходимости); реальный Telegram-бот и ручной прогон на Windows — отдельный ручной шаг приёмки TASK-093, не автоматические ворота.
- PostgreSQL для интеграционных и сквозных тестов — тестовая БД (Testcontainers или локальная тестовая PostgreSQL+pgvector, выбор фиксируется при реализации в TASK-090); пароль/доступы не коммитятся, берутся из конфигурации TASK-003.
