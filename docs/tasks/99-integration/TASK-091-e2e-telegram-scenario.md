# TASK-091 — Сквозной сценарий Telegram: сообщение Owner → ответ ассистента

## Цель

Один проверяемый результат: автоматический сквозной сценарий доказывает полный путь сообщения владельца в Telegram — приём, проверка Owner, маршрутизация Tier0–Tier3 с губернатором бюджета, при необходимости HITL-подтверждение кнопками Telegram и доставка ответа обратно в тот же чат — на реальной композиции TASK-090 и тестовой PostgreSQL.

## Контекст

- Telegram — первый канал (Q4), Avalonia и CLI развиваются параллельно и в этот сценарий не входят, кроме общей композиции. Только Owner: сообщения не-владельца не исполняются (TASK-073).
- Маршрутизация: Tier0 regex → Tier1 ONNX-эмбеддинг (`multilingual-e5-small`, не встроена, в тесте подменяется фейковым эмбеддингом той же размерности) + семантический кэш → Tier2/Tier3 LLM (в тесте — фейковый LLM-провайдер по контракту TASK-002). TokenBudgetGovernor с дефолтами $0.50/день, 4000/12000 токенов, 3/5 ходов — на реальной регистрации TASK-033, лимиты в тестовой конфигурации уменьшены для негативных веток.
- HITL: запрос подтверждения уходит в Telegram (кнопки Approve/Reject, TASK-046/TASK-060); до решения владельца действие с побочным эффектом не выполняется.
- Внешняя сеть и реальный бот-токен в автоматическом сценарии не используются: Telegram заменяется фейковым транспортом на границе контрактов TASK-002/TASK-060 (тот же фейк, что в тестах TASK-060). Реальный бот — ручная проверка TASK-093.

## Объём работ

- E2E-тест (to-be-created, `tests/CyberPipe.Tests.E2E/TelegramScenarioTests`, имя финализируется в TASK-001) на полной композиции TASK-090: тестовая PostgreSQL+pgvector, фейковые Telegram-транспорт, LLM и эмбеддинг, реальные роутер, губернатор, HITL и канал.
- Позитивный сценарий «команда с подтверждением»: Owner пишет команду, попадающую в навык с побочным эффектом и включённым HITL → бот присылает запрос подтверждения с кнопками → Owner нажимает Approve → навык исполняется ровно один раз → Owner получает итоговый ответ в тот же чат; расход записан губернатором, диалог и решение HITL видны в PostgreSQL.
- Позитивный сценарий «быстрый ответ без HITL»: команда Tier0/Tier1 без побочного эффекта → ответ без запроса подтверждения, кэш Tier1 при повторе той же команды даёт ответ без повторного вызова LLM-фейка (счётчик вызовов).
- Негативные ветки (каждая — отдельный проверяемый тест): сообщение не-владельца отклоняется без вызова роутера/навыка; Reject на HITL → навык не исполнен, Owner получает сообщение об отмене; исчерпанный тестовый дневной бюджет → отказ губернатора понятным сообщением, LLM и навык не вызваны; таймаут HITL → действие не исполнено, запуск помечен по политике TASK-046.
- Проверка доставки: итоговое сообщение приходит именно в исходный чат и связано с исходным сообщением (идентификаторы контрактов TASK-002), дубли при повторной доставке транспорта не плодит второй ответ (идемпотентность по ключу сообщения).

## Критерии приёмки

- [ ] Позитивный HITL-сценарий: порядок наблюдаемых событий — сообщение → запрос подтверждения → Approve → исполнение навыка (ровно 1 раз) → ответ в тот же чат; до Approve навык не вызывался.
- [ ] Быстрый сценарий: ответ без HITL; повтор команды обслуживается семантическим кэшем, счётчик вызовов LLM-фейка не вырос.
- [ ] Не-владелец: роутер и навык не вызваны (счётчики фейков), в лог TASK-004 записано отклонение без текста секретов.
- [ ] Reject и таймаут HITL: навык не исполнен ни разу, Owner получил финальное сообщение о невыполнении.
- [ ] Исчерпание бюджета: LLM и навык не вызваны, ответ содержит причину «бюджет» и текущие лимиты из конфигурации.
- [ ] Весь набор проходит на чистом окружении одной командой ниже, без сети и без реальных токенов Telegram/LLM.

## Тестирование

- Уровень: e2e.
- Как: полная композиция TASK-090 в тестовом хосте; PostgreSQL — Testcontainers или локальная тестовая БД (как зафиксировано в TASK-090); все внешние границы — фейки TASK-002 со счётчиками вызовов и очередью входящих «сообщений Telegram».
