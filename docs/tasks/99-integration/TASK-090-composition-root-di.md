# TASK-090 — Композиционный корень и DI: сборка Service, Desktop, CLI и Brainstem в единую систему

## Цель

Один проверяемый результат: все подсистемы областей 01–09 регистрируются в DI из единственного композиционного корня на каждый процесс (Service, Desktop, CLI, Brainstem), система стартует в заданном порядке до готовности принимать сообщения и останавливается без потери состояния в PostgreSQL.

## Контекст

- Канон: DECISIONS Q1–Q24 и ADR-001..ADR-008. Одна PostgreSQL + pgvector; Quartz.NET в той же PostgreSQL; собственные интерфейсы сообщений с заменяемым транспортом без фиксированного брокера; только Owner; DevTools/Git/Build и Guest отсутствуют.
- До этой задачи каждая область регистрирует только свои сервисы внутри своего проекта и тестируется на фейках контрактов TASK-002. Композиционный корень — первое место, где реальные реализации встречаются; обратных зависимостей областей от этой задачи нет.
- Процессы: Service (служба Windows, `Program Files`, работает постоянно), Desktop (Avalonia, все ОС, закрывается независимо, управляет Service), CLI (параллельный канал), Brainstem (изолированный worker, запускается и надзирается Service, сам внешних каналов не имеет).
- Кода ещё нет (`CyberPipe.slnx` пуст); пути ниже — to-be-created по раскладке TASK-001: `src/CyberPipe.Service/`, `src/CyberPipe.Desktop/`, `src/CyberPipe.Cli/`, `src/CyberPipe.Brainstem/`, feature-проекты областей, `src/CyberPipe.Contracts/`.

## Объём работ

- Модули регистрации DI (по одному на область, в проектах областей — только регистрация, без логики): `AddCyberPipeData`, `AddCyberPipeRouter`, `AddCyberPipeChains`, `AddCyberPipeSkills`, `AddCyberPipeChannels`, `AddCyberPipeSecurity`, `AddCyberPipeModels` (имена финализируются с владельцами областей при реализации, сигнатуры — `IServiceCollection` + конфигурация TASK-003). Транзитные регистрации внутри модулей запрещены скрытно: каждый модуль регистрирует только свои типы.
- Композиционные корни четырёх процессов (to-be-created):
  - Service: хост TASK-020 + данные, Quartz (TASK-045), роутер Tier0–Tier3 и TokenBudgetGovernor (TASK-030..034), исполнитель цепочек (TASK-044), скиллы (TASK-050..053), безопасность (TASK-070..073), каталоги/установщик моделей (TASK-080..082), каналы как потребители транспорта (Telegram — TASK-060), надзор Brainstem (TASK-022), песочница (TASK-023).
  - Desktop: Avalonia UI (TASK-061) + клиент управления службой (TASK-021) + локальный просмотр состояния только через контракты TASK-002; прямой ссылки на проект данных и PostgreSQL-драйвер у Desktop нет.
  - CLI: команды TASK-062 через те же контракты, что Desktop; собственная регистрация бизнес-сервисов в CLI запрещена.
  - Brainstem: только Contracts + свой worker-контур TASK-022; регистрация каналов, UI и цепочек в Brainstem запрещена архитектурным тестом.
- Порядок запуска Service (каждый шаг — с таймаутом и понятной ошибкой в лог TASK-004): 1) конфигурация и секреты (TASK-003), fail-fast при отсутствии обязательных значений; 2) подключение к PostgreSQL: при неудаче — состояние «требуется восстановление подключения» и запрос пароля у пользователя (Q21), а не аварийный выход в цикле; 3) миграции (TASK-011); 4) Quartz.NET на той же PostgreSQL (TASK-045); 5) транспорт сообщений (одна реализация `IMessageTransport` из конфигурации; замена реализации — только конфигурацией, код логики не меняется); 6) роутер, губернатор бюджета с дефолтами $0.50/день, 4000/12000 токенов, 3 облачных / 5 локальных ходов (всё из конфигурации); 7) исполнитель цепочек + восстановление незавершённых запусков (TASK-044); 8) каналы и HITL-доставка (TASK-046, TASK-060).
- Порядок остановки: стоп приёма новых сообщений → остановка Quartz → завершение/чекпоинт активных цепочек → стоп каналов → закрытие пула PostgreSQL. Остановка не удаляет и не «откатывает» завершённые чекпоинты.
- Health/готовность: внутренний статус по контракту TASK-002 (БД доступна, миграции применены, Quartz запущен, транспорт подключён, Brainstem жив); Desktop/CLI показывают его через `IServiceControl` и статус-контракты. Первый запуск: если БД и Owner не настроены, Service стартует в ограниченном режиме, а мастер первого запуска (TASK-063) доступен из Desktop/CLI и предлагает стандартный эмбеддинг `multilingual-e5-small` для Tier1 (сама установка — TASK-081, здесь только вызов по контракту).
- Диагностический прогон конфигурации (`--validate-config`, имя ключа финализируется при реализации): проверяет связность DI-графа (все контракты TASK-002, потребляемые зарегистрированными сервисами, разрешимы), наличие каталогов моделей 15+8 JSON (TASK-080) и отсутствие запрещённых регистраций (Guest, DevTools/Git/Build) — без запуска каналов и без записи в БД, кроме проверки подключения.

## Контракты и интерфейсы

- Потребляет все публичные контракты TASK-002 (`IMessageBus`, `IMessageTransport`, `IIntentRouter`, `ITokenBudgetGovernor`, `IServiceControl`, DTO цепочек, моделей и HITL) — только как точки регистрации; новых публичных бизнес-интерфейсов задача не вводит.
- Вводит (to-be-created, внутреннее для хостов): модули регистрации областей (см. «Объём работ»), `IStartupStatus`/статус готовности по DTO TASK-002, точка входа `--validate-config`.
- Инварианты графа: `CyberPipe.Contracts` ни на что не ссылается; Desktop и CLI не ссылаются на проект данных и драйвер PostgreSQL; Brainstem ссылается только на Contracts и свой контур; feature-проекты не ссылаются друг на друга в обход Contracts (проверяется архитектурными тестами TASK-001).

## Результаты

- Четыре композиционных корня, модули регистрации областей, порядок запуска/остановки Service, статус готовности, режим `--validate-config`, архитектурные тесты графа процессов.

## Критерии приёмки

- [ ] `--validate-config` на эталонной конфигурации завершается успешно; удаление одной обязательной регистрации или секрета даёт именованную ошибку с указанием контракта/ключа, а не `NullReferenceException`.
- [ ] Service на тестовой PostgreSQL проходит весь порядок запуска до статуса «готов», принимает ping-сообщение через фейковый транспорт и отвечает; статус готовности виден из Desktop-фейка и CLI по контрактам.
- [ ] Подмена реализации `IMessageTransport` только конфигурацией (вторая тестовая реализация) не требует правок кода логики: тот же ping-сценарий проходит.
- [ ] Остановка Service посреди активной тестовой цепочки: после повторного запуска чекпоинты в PostgreSQL целы, незавершённый запуск обрабатывается политикой восстановления TASK-044.
- [ ] Недоступная БД при старте: Service не падает в цикл рестартов, переходит в состояние восстановления подключения и запрашивает пароль; после ввода верного пароля продолжает запуск с шага миграций.
- [ ] Архитектурные тесты: у Desktop/CLI нет ссылки на данные/драйвер PostgreSQL; у Brainstem нет каналов/UI/цепочек; в DI-графе нет сервисов Guest и DevTools/Git/Build; поиск по исходникам не находит Hangfire и отдельных баз подсистем.

## Тестирование

- Уровень: integration (композиция) + architecture.
- Как: тестовая PostgreSQL + pgvector (Testcontainers или локальная тестовая БД — фиксируется при реализации); фейковые транспорт, LLM-провайдеры и Telegram на границах TASK-002; реальные регистрации всех модулей. Сценарии: холодный старт, старт без БД, подмена транспорта, остановка/рестарт, `--validate-config` на полной и на урезанной конфигурации. Модульные тесты областей здесь не дублируются.
