# TASK-073 — Owner auth whitelist

## Цель

Пускать к CyberPipe только владельца (Owner) во всех каналах — Telegram, Avalonia Desktop, CLI — по белому списку идентификаторов, отклоняя всех остальных без гостевого или анонимного режима.

## Контекст

- Решение Q18 (DECISIONS.md): Guest полностью удалён, существует только Owner. Никаких ролей ниже Owner, демо-доступа и «гостевых» команд в системе нет.
- Каналы развиваются параллельно (Q19): Telegram — первый канал (TASK-060), Avalonia Desktop (TASK-061), CLI/TUI (TASK-062). Каждый канал устанавливает личность отправителя по-своему (Telegram user id, локальная учётная запись/сессия Desktop, локальный пользователь CLI), а решение «это Owner или нет» должно быть единым.
- Desktop и Service — раздельные процессы (Q24): Desktop управляет Service (TASK-021), но авторизация команд к Service проходит ту же проверку Owner, а не факт запуска Desktop.
- HITL-подтверждения (TASK-046) действительны только от Owner: подтверждение от идентификатора вне белого списка не засчитывается — проверка переиспользует этот же авторизатор.
- Белый список — чувствительная конфигурация: хранится и меняется по TASK-003 (секреты/конфигурация), первичное заполнение — мастер первого запуска (TASK-063).
- Код отсутствует (`CyberPipe.slnx` пуст); проекты помечены как «к созданию».

## Объём работ

- Создать в проекте безопасности (к созданию: `src/CyberPipe.Security/`) авторизатор Owner по контрактам TASK-002.
- Модель принципала канала: канал, идентификатор отправителя (Telegram user id, локальный SID/имя пользователя, идентификатор сессии), отображаемое имя (только для журнала, не для решения).
- Белый список по каналам из конфигурации (TASK-003): список разрешённых идентификаторов для Telegram, Desktop, CLI; пустой список для канала означает «канал закрыт», а не «открыт всем».
- Решение: `Authorized` только при точном совпадении идентификатора с белым списком соответствующего канала; совпадение по отображаемому имени/username без идентификатора не авторизует (username в Telegram меняется).
- Fail-closed: неизвестный канал, пустой идентификатор, недоступная/битая конфигурация белого списка, сбой чтения конфигурации — `Denied` для всех, включая ранее авторизованных, с записью в журнал.
- Перечитывание конфигурации без перезапуска Service: изменение белого списка (добавление/удаление идентификатора) применяется к следующим проверкам; отзыв идентификатора действует немедленно со следующей проверки.
- Журналирование каждой проверки (канал, идентификатор в усечённом/хэшированном виде, решение) через TASK-004; полные идентификаторы и содержимое сообщений в общий журнал не пишутся.
- Контракт для мастера первого запуска (TASK-063) и UI (TASK-061): чтение текущего белого списка и проверка «список не пуст хотя бы для одного канала» — без реализации самих UI и мастера в этой задаче.

## Вне рамок

- Установление личности внутри канала (Telegram Bot API update, локальная сессия Avalonia, аргументы CLI) — TASK-060/TASK-061/TASK-062; здесь только решение по готовому принципалу.
- Роли, права на отдельные команды и гостевой доступ — не реализуются принципиально (только Owner, Q18).
- HITL-механизм и доставка подтверждений — TASK-046; здесь только переиспользуемая проверка «подтвердил Owner».
- Хранение секретов, шифрование конфигурации и мастер первого запуска как UI — TASK-003/TASK-063; здесь только чтение белого списка через абстракцию.
- Управление Service (старт/стоп/перезапуск) — TASK-021; авторизатор только отвечает, может ли принципал отдавать команды.

## Контракты и интерфейсы

Используются абстракции из TASK-002 (точные имена — по факту TASK-002, ниже — требуемая семантика):

- `IOwnerAuthorizer`:
  - `Task<OwnerAuthDecision> AuthorizeAsync(ChannelPrincipal principal, CancellationToken ct)` — проверка входящего сообщения/команды.
  - `Task<bool> IsOwnerAsync(ChannelPrincipal principal, CancellationToken ct)` — короткая форма для HITL (TASK-046) и управления Service (TASK-021).
  - `Task<OwnerWhitelistSnapshot> GetWhitelistSnapshotAsync(CancellationToken ct)` — каналы и число идентификаторов (без раскрытия полных идентификаторов наружу UI-логам).
- `ChannelPrincipal`: канал (`Telegram` / `Desktop` / `Cli` / `Webhook` / иное по TASK-002), идентификатор отправителя, отображаемое имя (необязательно, в решении не участвует).
- `OwnerAuthDecision`: исход (`Authorized` / `Denied`), код причины (`NotInWhitelist`, `EmptyWhitelist`, `MissingIdentity`, `UnknownChannel`, `WhitelistUnavailable`).
- `IOwnerWhitelistProvider` (абстракция из TASK-002 поверх конфигурации TASK-003): отдаёт актуальный белый список по каналам и сигнал об его изменении; авторизатор не читает файлы конфигурации напрямую.
- Webhook как источник триггеров (TASK-041): принципалом является не Owner-личность, а подпись/секрет Webhook по TASK-003; авторизатор Owner такие запросы не авторизует как Owner и возвращает `Denied` с `UnknownChannel`/отдельной причиной — проверка подписи Webhook остаётся за TASK-041.

## Результаты

- Реализация `IOwnerAuthorizer` в проекте безопасности (к созданию).
- Семантика по умолчанию: пустой белый список канала = канал закрыт; Guest-режима и анонимного fallback нет ни в коде, ни в конфигурации.
- Unit-тесты белого списка, fail-closed поведения и немедленного отзыва идентификатора.

## Критерии приёмки

- Идентификатор из белого списка своего канала получает `Authorized`; тот же идентификатор в чужом канале без записи в его списке — `Denied`.
- Совпадение только по отображаемому имени/username при несовпадающем идентификаторе даёт `Denied`.
- Пустой белый список канала, пустой идентификатор и неизвестный канал дают `Denied` (fail-closed); опции «разрешить всем»/Guest в конфигурации не существует.
- При недоступной или битой конфигурации белого списка все проверки дают `Denied` с причиной `WhitelistUnavailable`, а не последнее закешированное `Authorized`.
- Удаление идентификатора из конфигурации применяется к следующей проверке без перезапуска (тест со сменой снимка провайдера).
- Журнал проверок не содержит полных идентификаторов и содержимого сообщений (тест с фейковым журналом TASK-004).

## Тестирование

- Уровень: unit.
- Как: фейковый `IOwnerWhitelistProvider` со сменными снимками (пустой/один/несколько идентификаторов, битая конфигурация, смена на лету); табличные тесты по каналам Telegram/Desktop/CLI; тесты «имя совпало — идентификатор нет», «отзыв без перезапуска», fail-closed на бросающем исключение провайдере; фейковый журнал для проверки хэширования идентификаторов. Реальные Telegram/Desktop/CLI и PostgreSQL не требуются.
