# TASK-072 — Egress sanitizer

## Цель

Очищать все исходящие за пределы локальной машины данные (облачные LLM, Webhook-Delivery, внешние API) от секретов, ключей, токенов и персональных данных до отправки: маскировать найденное, блокировать отправку при критичной чувствительности и возвращать отчёт о находках без самих секретов.

## Контекст

- CyberPipe — локальный ассистент одного Owner; локальные данные (PostgreSQL, заметки, CRM, финансы — TASK-051) не должны утекать в облачные модели и внешние Webhook в исходном виде.
- Исходящие пути: Tier 2/3 облачные LLM (TASK-032), Delivery в цепочках `Trigger -> Skill -> Script -> Delivery` (TASK-044), Webhook-триггеры/доставка (TASK-041), Telegram-канал (TASK-060). Транспорт заменяем, брокер не фиксирован; очистка выполняется вызывающей стороной по контракту TASK-002 до передачи транспорту.
- Секреты приложения хранятся по TASK-003 и в исходящие payload никогда не включаются вызывающими осознанно; sanitizer — последний барьер от случайного включения (логи, тексты заметок, выводы скриптов `skill-hack.*`).
- Классификация — по смыслу класса значения (секрет/ключ/токен/ПДн), а не по закрытому списку имён полей: полные имена, алиасы и длинные формы (`apiKey`, `api_key`, `API key`, `ключ доступа`, `password`, `пароль`, `connectionString` и т.п.) относятся к одному классу; неизвестное, но правдоподобно чувствительное значение обрабатывается fail-closed (маскирование), а не пропускается как есть.
- Код отсутствует (`CyberPipe.slnx` пуст); проекты помечены как «к созданию».

## Объём работ

- Создать в проекте безопасности (к созданию: `src/CyberPipe.Security/`) sanitizer исходящих payload по контрактам TASK-002.
- Поддерживаемые формы payload: свободный текст, пары ключ-значение, JSON (рекурсивный обход), заголовки/параметры Webhook. Результат сохраняет структуру и типы нечувствительных значений.
- Детекторы по классам значений:
  - секреты: API-ключи и токены (префиксы провайдеров, Bearer/JWT, высокая энтропия по порогу конфигурации), пароли, строки подключения PostgreSQL/иные, приватные ключи (PEM);
  - сетевые/служебные: значения из хранилища секретов TASK-003 по точному совпадению (список «известных секретов» подаётся через абстракцию, без чтения файлов секретов напрямую);
  - ПДн: e-mail, телефон, паспорт/СНИЛС-подобные номера, номера карт (с проверкой Луна) — маскируются частично по политике класса.
- Имена полей: нормализация имени (регистр, разделители, camelCase/snake_case) и сопоставление по классу, включая полные и сокращённые формы; поле с неузнанным именем, но секретоподобным значением (энтропия/шаблон), также маскируется — пропуск «как есть» допустим только для значений вне классов чувствительности.
- Действия по классам (конфигурация TASK-003): `Mask` (полная замена плейсхолдером), `PartialMask` (e-mail/карта: видимый минимум), `Block` (критичные: приватные ключи, строки подключения с паролем — payload не отправляется).
- Отчёт: список находок (класс, путь поля/позиция, действие) без значений секретов; исходный payload вызывающему не мутируется — sanitizer возвращает копию.
- Fail-closed: непарсибельный JSON при заявленном типе JSON, сбой детектора или превышение лимита размера payload (конфигурация) дают `Block` с причиной, а не отправку оригинала.
- Журналирование факта очистки/блокировки (адресат-класс: `CloudLlm`/`Webhook`/`Telegram`/прочее, число находок по классам) через TASK-004, без содержимого.

## Вне рамок

- Сама отправка, транспорты и ретраи — TASK-032/TASK-041/TASK-044/TASK-060; sanitizer сеть не использует.
- Хранение и ротация секретов — TASK-003; здесь только потребление списка известных секретов через абстракцию.
- Входящая фильтрация и prompt-injection защита входящих данных — не входит; задача только про egress.
- Авторизация Owner и anti-wipe — TASK-073/TASK-070.
- Шифрование БД/транспортов (TLS, шифрование PostgreSQL) — TASK-010 и настройки транспорта, не sanitizer.

## Контракты и интерфейсы

Используются абстракции из TASK-002 (точные имена — по факту TASK-002, ниже — требуемая семантика):

- `IEgressSanitizer`:
  - `Task<EgressSanitizeResult> SanitizeAsync(EgressPayload payload, CancellationToken ct)`.
- `EgressPayload`: класс адресата (`CloudLlm` / `Webhook` / `ExternalApi` / `Telegram`), вид содержимого (`Text` / `KeyValue` / `Json`), содержимое, метаданные источника (цепочка/навык/канал).
- `EgressSanitizeResult`: исход (`Allowed` с очищенной копией / `Blocked`), очищенный payload (при `Allowed`), находки: `SanitizeFinding` (класс значения: `ApiKey`/`Token`/`Password`/`ConnectionString`/`PrivateKey`/`Email`/`Phone`/`CardNumber`/`KnownSecret`/`HighEntropyValue`; путь поля или позиция; действие `Mask`/`PartialMask`/`Block`), причина блокировки при `Blocked`.
- `IKnownSecretsProvider` (абстракция из TASK-002 поверх TASK-003): отдаёт отпечатки/значения известных секретов только для сравнения внутри sanitizer; значения наружу не возвращаются.
- Политика классов (действие по умолчанию, порог энтропии, лимит размера) — конфигурация TASK-003.

## Результаты

- Реализация `IEgressSanitizer` в проекте безопасности (к созданию).
- Политика по умолчанию: приватные ключи и строки подключения с паролем — `Block`, ключи/токены/пароли — `Mask`, e-mail/карты — `PartialMask`.
- Unit-тесты детекторов, нормализации имён, fail-closed поведения и немутации оригинала; пробный тест на не перечисленном заранее варианте имени поля секрета (полная/длинная форма).

## Критерии приёмки

- API-ключ, Bearer/JWT-токен, пароль и строка подключения с паролем в тексте, JSON и парах ключ-значение обнаруживаются; приватный ключ и строка подключения дают `Blocked`, остальные — маскируются плейсхолдером, секрет в результате и отчёте отсутствует (проверка поиском исходного значения).
- Одно и то же секретное значение под коротким (`key`), полным (`apiKey`) и длинным словесным (`API key` / «ключ доступа») именем поля маскируется во всех случаях; значение высокой энтропии под нейтральным именем также маскируется.
- E-mail и номер карты, проходящий проверку Луна, маскируются частично; случайная цифра, не проходящая Луна, картой не считается.
- Исходный payload после вызова не изменён; очищенный JSON сохраняет структуру и нечувствительные значения/типы.
- Битый JSON при виде `Json`, превышение лимита размера и сбой детектора дают `Blocked` (fail-closed), оригинал вызывающему для отправки не возвращается как очищенный.
- Чистый payload без находок возвращается равным оригиналу с пустым списком находок и исходом `Allowed`.

## Тестирование

- Уровень: unit.
- Как: табличные фикстуры payload по классам секретов/ПДн (текст/JSON/пары, RU/EN имена полей, алиасы и длинные формы, включая вариант, не перечисленный в детекторе дословно); фейковый `IKnownSecretsProvider`; подсчёт энтропии на контрольных строках; тесты немутации оригинала и отсутствия секретов в отчёте/журнале (фейк TASK-004). Сеть, PostgreSQL и реальные секреты не используются — только синтетические значения.
