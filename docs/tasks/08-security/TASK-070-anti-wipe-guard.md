# TASK-070 — Anti-wipe guard

## Цель

Не допускать необратимого уничтожения данных CyberPipe (БД, файлов данных, конфигурации) без явного подтверждения Owner: классифицировать деструктивные операции и возвращать решение «разрешить / запретить / требуется подтверждение» до их исполнения.

## Контекст

- CyberPipe — локальный персональный ассистент (.NET 10), единственный владелец — Owner (Guest удалён, Q18), одна PostgreSQL + pgvector.
- Цепочки только `Trigger -> Skill -> Script -> Delivery`; скрипты исполняются в sandbox (Restricted Token + Job Object + Deny-ACL, TASK-023), но sandbox ограничивает процесс, а не семантику операции: разрешённый скрипт всё ещё может удалить данные внутри разрешённой области.
- Anti-wipe guard — семантический барьер поверх sandbox: проверяет намерение операции до выполнения вызывающей стороной (исполнителем цепочек TASK-044, навыками, каналами).
- Механизм HITL-подтверждений — TASK-046 (Telegram/Avalonia); guard только возвращает `RequireApproval`, не взаимодействует с UI.
- Код отсутствует (`CyberPipe.slnx` пуст); проекты помечены как «к созданию».

## Объём работ

- Создать проект безопасности (к созданию: `src/CyberPipe.Security/`) и реализацию guard по контрактам TASK-002.
- Классификатор деструктивных операций по типу и цели:
  - SQL: `DROP DATABASE/TABLE/SCHEMA`, `TRUNCATE`, `DELETE`/`UPDATE` без `WHERE`, массовое удаление по оценке затронутых строк выше порога;
  - файловая система: рекурсивное удаление, удаление защищённых путей (каталог данных, конфигурация, резервные копии, каталог пакетов `skill-hack.*`), перезапись файла конфигурации/секретов;
  - служебные: очистка всей БД/кэша, удаление всех цепочек/расписаний Quartz, сброс конфигурации к заводской.
- Защищённые пути и пороги — из конфигурации (TASK-003): список путей/префиксов, порог массового удаления, режим по умолчанию для неклассифицированных операций.
- Решения: `Allow` (обратимая/точечная операция), `Deny` (прямой запрет: например, удаление каталога данных или `DROP DATABASE` без флага подтверждения в контракте), `RequireApproval` (разрушительная, но легитимная операция — вызывающая сторона запрашивает HITL по TASK-046 и повторно вызывает guard с подтверждённым токеном/флагом).
- Одноразовость подтверждения: подтверждение привязано к отпечатку операции (тип + цель + нормализованные параметры), повтор/подмена параметров требует нового подтверждения.
- Журналирование каждого решения (тип операции, цель в обезличенном виде, решение, источник/канал) через диагностику TASK-004; секреты и содержимое в журнал не пишутся.
- Fail-closed: ошибка классификации, пустая/неразобранная операция или недоступность конфигурации защищённых путей даёт `Deny`, а не `Allow`.

## Вне рамок

- Sandbox процессов (Restricted Token, Job Object, Deny-ACL) — TASK-023; guard процессы не запускает и не ограничивает.
- HITL-рендеринг и доставка подтверждений — TASK-046, каналы TASK-060/TASK-061; здесь только решение `RequireApproval`.
- Резервное копирование и восстановление данных — не входит в задачу; guard только предотвращает удаление, бэкапы не создаёт.
- Egress-очистка исходящих данных — TASK-072; авторизация Owner — TASK-073.
- Миграции схемы и репозитории — TASK-011/TASK-013; журнал решений хранится через абстракцию из TASK-002 либо только в логе TASK-004, собственная таблица в этой задаче не создаётся.

## Контракты и интерфейсы

Используются абстракции из TASK-002 (точные имена — по факту TASK-002, ниже — требуемая семантика):

- `IAntiWipeGuard`:
  - `Task<WipeGuardDecision> EvaluateAsync(DestructiveOperation operation, CancellationToken ct)` — проверка до исполнения.
  - `Task<WipeGuardDecision> EvaluateConfirmedAsync(DestructiveOperation operation, ApprovalProof proof, CancellationToken ct)` — повторная проверка после HITL-подтверждения.
- `DestructiveOperation`: вид (`SqlStatement` / `FileDelete` / `FileOverwrite` / `BulkDataClear` / `ServiceReset`), цель (имя таблицы, путь, идентификатор ресурса), нормализованный текст/параметры, оценка объёма (число строк/файлов, если известна), источник (канал, цепочка, навык), флаг обратимости от вызывающего.
- `WipeGuardDecision`: исход (`Allow` / `Deny` / `RequireApproval`), код причины (`ProtectedPath`, `DropStatement`, `MissingWhereClause`, `BulkThresholdExceeded`, `UnclassifiedDestructive`, `ClassifierFailure`), отпечаток операции для привязки подтверждения.
- `ApprovalProof`: идентификатор подтверждения из TASK-046 и отпечаток операции; guard сверяет отпечатки, сам подтверждения не выдаёт и не хранит UI-состояние.
- Конфигурация защищённых путей/порогов — секция из TASK-003, читается через абстракцию конфигурации TASK-002.

## Результаты

- Реализация `IAntiWipeGuard` в проекте безопасности (к созданию: `src/CyberPipe.Security/`).
- Конфигурация по умолчанию: защищённые пути данных/конфигурации/бэкапов, порог массового удаления, fail-closed режим.
- Unit-тесты классификации, fail-closed поведения и одноразовости подтверждения.

## Критерии приёмки

- `DROP TABLE`, `TRUNCATE` и удаление защищённого пути возвращают `Deny` или `RequireApproval` согласно конфигурации и никогда — `Allow`.
- `DELETE` без `WHERE` классифицируется как деструктивная операция; точечный `DELETE`/`UPDATE` с `WHERE` и оценкой ниже порога возвращает `Allow`.
- Рекурсивное удаление пути вне защищённого списка, но с числом файлов выше порога, возвращает `RequireApproval`; ниже порога — `Allow`.
- Подтверждение, выданное на одну операцию, не проходит для операции с изменённой целью или параметрами (отпечаток не совпадает) — возвращается `RequireApproval` повторно.
- Неклассифицируемая операция, пустой ввод и сбой классификации возвращают `Deny` (fail-closed) с кодом причины и записью в журнале без секретов.
- Guard не исполняет операции сам: в реализации отсутствуют вызовы файловой системы, SQL-исполнения и запуска процессов (проверяется тестом со строгими фейками и обзором зависимостей проекта).

## Тестирование

- Уровень: unit.
- Как: табличные тесты «операция → решение/причина» для каждого вида операций; фейковый провайдер конфигурации (защищённые пути, пороги); фейковый журнал диагностики TASK-004 для проверки обезличенных записей; тесты отпечатка подтверждения (совпадение/подмена цели/повторное использование); тест fail-closed на бросающем исключение классификаторе. PostgreSQL, файловая система и HITL не требуются — только фейки контрактов TASK-002.
