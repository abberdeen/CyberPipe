# TASK-032 — Tier 2/3: LLM-роутер (лёгкая и тяжёлая модели)

## Цель

Классифицировать сложные запросы, не решённые Tier 0/1, сначала лёгкой LLM (Tier 2), а при низкой уверенности — тяжёлой LLM (Tier 3), с обязательной проверкой бюджета токенов.

## Контекст

- Верхние ярусы маршрутизации CyberPipe: Tier 2 — быстрая/дешёвая модель, Tier 3 — самая способная из настроенных.
- Модели не встроены: локальные разворачиваются через Ollama (например, Qwen3, настройка — TASK-081), облачные — по каталогам TASK-080. Выбор конкретной модели — конфигурация (TASK-003), а не код.
- Каждый LLM-вызов предварительно авторизуется TokenBudgetGovernor (TASK-033): дневной бюджет по умолчанию $0.50, лимиты 4000/12000 токенов, до 3 облачных / 5 локальных ходов — все значения конфигурируемы.
- Результат LLM-роутера — intent + параметры для цепочек `Trigger -> Skill -> Script -> Delivery`, а не свободный ответ пользователю.

## Объём работ

- Промпт классификации: список допустимых intent-ов с описаниями, требование структурированного ответа (JSON по схеме из TASK-002), few-shot примеры из конфигурации.
- Tier 2: вызов лёгкой модели через абстракцию чат-модели (TASK-002); парсинг и валидация JSON; при уверенности ≥ порога — `Matched`.
- Tier 3: эскалация на тяжёлую модель при низкой уверенности Tier 2, невалидном ответе или явной сложности запроса.
- Интеграция с TASK-033: запрос разрешения до вызова, учёт фактических токенов после вызова; при отказе бюджета — `Escalate`/терминальный статус `BudgetDenied` без вызова модели.
- Обработка ошибок провайдера: тайм-ауты, недоступность локальной модели, ошибки облачного API — ограниченные повторы с backoff только для транзиентных ошибок; далее терминальный статус с причиной.
- Опциональная запись уверенных результатов Tier 2/3 в семантический кэш через интерфейс TASK-034 (если включён в конфигурации).

## Вне рамок

- Реализация провайдеров моделей и каталоги — TASK-080, TASK-081; здесь только потребление абстракций TASK-002.
- Учёт бюджета и его хранение — TASK-033.
- Генерация свободных ответов и диалоги — навыки/цепочки области 05–06.
- Regex и эмбеддинги — TASK-030, TASK-031.

## Зависимости

- TASK-033

## Контракты и интерфейсы

- Реализует контракт яруса из TASK-002: `TryRouteAsync(RouteRequest) -> RouteResult`; терминальные статусы включают `Matched`, `BudgetDenied`, `Failed` с диагностической причиной.
- `IChatModelProvider` (по TASK-002): вызов по логическому имени/классу модели (`Light` / `Heavy`), возврат текста и usage (токены входа/выхода).
- `ITokenBudgetGovernor` (TASK-033): `TryAuthorizeAsync(estimate)`, `RecordUsageAsync(actual)`.
- `ISemanticCache` (TASK-034) — опционально, только через интерфейс.
- Схема JSON-ответа классификации (intent, параметры, уверенность 0..1) фиксируется в контрактах TASK-002; невалидный JSON не считается совпадением.

## Результаты

- Реализация Tier 2/3 в проекте роутера (к созданию: `src/CyberPipe.Router/`).
- Шаблоны промптов и список intent-ов в конфигурации по умолчанию.
- Unit-тесты на фейковых моделях: эскалация, бюджет, парсинг, ошибки.

## Критерии приёмки

- Уверенный валидный ответ Tier 2 возвращает `Matched` без вызова Tier 3 (проверяется фейками).
- Низкая уверенность или невалидный JSON Tier 2 вызывает ровно одну эскалацию на Tier 3.
- При отказе TokenBudgetGovernor модель не вызывается; возвращается `BudgetDenied`.
- Фактический usage передаётся в governor после каждого вызова, включая неуспешные попытки с ненулевым usage, если провайдер его вернул.
- Недоступность модели завершается `Failed` с причиной за ограниченное число попыток, без зависания (тайм-ауты соблюдены).

## Тестирование

- Уровень: unit + contract.
- Как: фейковые `IChatModelProvider` со сценариями ответов (валидный/невалидный JSON, низкая уверенность, исключения, тайм-аут); фейковый governor (разрешает/запрещает); contract-тесты схемы JSON классификации против фикстур из TASK-002. Реальные модели и сеть в тестах не используются.
