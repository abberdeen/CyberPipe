# TASK-031 — Tier 1: семантический роутер на ONNX-эмбеддингах

## Цель

Классифицировать запросы по семантической близости к эталонным примерам intent-ов с помощью локальной ONNX-модели эмбеддингов, без обращения к LLM при достаточной уверенности.

## Контекст

- Второй ярус маршрутизации CyberPipe: после промаха Tier 0 (TASK-030) и перед LLM-ярусами (TASK-032).
- Стандартная мультиязычная модель эмбеддингов для Tier 1 — `multilingual-e5-small`; предлагается при первом запуске (TASK-063), устанавливается/настраивается инструментом UI (TASK-081). Модель не встраивается в приложение.
- Эталонные примеры и эмбеддинги хранятся в единственной БД PostgreSQL + pgvector (TASK-012).
- Перед классификацией Tier 1 консультируется семантический кэш (TASK-034) через его интерфейс; реализация кэша — отдельная задача.

## Объём работ

- Интеграция ONNX Runtime: загрузка модели из настроенного пути, токенизация, получение эмбеддинга запроса; нормализация вектора.
- Загрузка эталонных примеров intent-ов (текст примера → intent) из конфигурации/БД; вычисление и сохранение их эмбеддингов через TASK-012 при старте/изменении набора.
- Классификация: косинусная близость к эталонам, выбор лучшего intent; при близости ≥ порога — `Matched`, иначе `Escalate` на Tier 2.
- Проверка семантического кэша (интерфейс TASK-034) до вычисления эмбеддинга эталонов; запись результата в кэш после уверенной классификации.
- Деградация: при отсутствии/недоступности модели или БД — `Escalate` с логированием причины, без падения роутера.
- Конфигурируемые пороги: порог совпадения, минимальный отрыв от второго кандидата (margin).

## Вне рамок

- Реализация хранилища pgvector — TASK-012; реализация кэша — TASK-034.
- Установка модели и мастер первого запуска — TASK-081, TASK-063.
- LLM-классификация — TASK-032; regex — TASK-030.
- Обучение/дообучение моделей и подбор эталонов через UI.

## Зависимости

## Контракты и интерфейсы

- Реализует тот же контракт яруса, что TASK-030 (`TryRouteAsync(RouteRequest) -> RouteResult`), семантика — по TASK-002.
- `IEmbeddingProvider` (по TASK-002): `Task<float[]> EmbedAsync(string text, CancellationToken ct)`; размерность соответствует `multilingual-e5-small`.
- `IEmbeddingStore` (TASK-012): поиск ближайших эталонов по вектору, upsert эталонов.
- `ISemanticCache` (контракт TASK-034): `TryGetAsync(embedding)`, `PutAsync(embedding, RouteResult)`.
- `RouteResult` при совпадении содержит intent, уверенность = близость, источник `Tier1`.

## Результаты

- Реализация Tier 1 в проекте роутера (к созданию: `src/CyberPipe.Router/`).
- Стартовый набор эталонных примеров (русский + английский) для базовых intent-ов в конфигурации.
- Тесты: unit на логику порогов/margin на фейковых эмбеддингах; component на ONNX-инференс с тестовой моделью/фикстурой.

## Критерии приёмки

- Запрос, близкий к эталону (близость ≥ порога и отрыв ≥ margin), возвращает `Matched` с верным intent.
- Запрос без близких эталонов возвращает `Escalate`.
- При недоступной модели/БД возвращается `Escalate`, исключение наружу не пробрасывается, причина залогирована.
- Попадание в семантический кэш возвращает кэшированный результат без ONNX-инференса эталонов (проверяется фейками).
- Эмбеддинги эталонов пересчитываются только при изменении набора примеров.

## Тестирование

- Уровень: unit + component.
- Как: unit — фейковый `IEmbeddingProvider` с предзаданными векторами, проверка порогов, margin и деградации; component — реальный ONNX-инференс на фикстуре коротких текстов (модель подменяется малой тестовой, если полная недоступна в CI) и фейковый/контейнерный `IEmbeddingStore`. Интеграция с реальным PostgreSQL здесь не требуется — моки/фейки по контрактам TASK-012.
