# TASK-034 — Семантический кэш маршрутизации

## Цель

Повторно использовать ранее принятые решения маршрутизации для семантически близких запросов, сокращая обращения к LLM-ярусам и задержку ответа.

## Контекст

- Кэш обслуживает Tier 1 (TASK-031) и, опционально, Tier 2/3 (TASK-032): ключ — эмбеддинг запроса, значение — принятый `RouteResult` (intent + параметры-шаблон).
- Хранение — единственная БД PostgreSQL + pgvector (TASK-012); отдельной кэш-инфраструктуры и внешнего брокера/Redis не вводится.
- Модель эмбеддингов — `multilingual-e5-small` (Tier 1); записи кэша версионируются по модели/размерности, чтобы смена модели не давала ложных попаданий.
- Кэшируются только уверенные детерминированные решения; ответы с чувствительными параметрами и `BudgetDenied`/`Failed` не кэшируются.

## Объём работ

- Реализация `ISemanticCache`: поиск по эмбеддингу с порогом близости, запись результата, инвалидация.
- Политика записи: только `Matched` с уверенностью ≥ конфигурируемого порога; сохранение intent, уверенности, времени, версии модели эмбеддингов.
- Политика чтения: попадание при близости ≥ порога кэша (отдельный порог, по умолчанию не ниже порога Tier 1); возврат результата с пометкой источника `SemanticCache`.
- TTL и ограничение объёма: фоновая/ленивая чистка устаревших записей, конфигурируемый максимум записей (вытеснение самых старых/редких).
- Невалидность при смене модели эмбеддингов или набора intent-ов: записи старой версии игнорируются и чистятся.
- Метрики попаданий/промахов для диагностики (TASK-004); ручная полная очистка для тестов и UI-вызова через интерфейс.

## Вне рамок

- Вычисление эмбеддингов — TASK-031 (`IEmbeddingProvider`); хранилище pgvector — TASK-012.
- Классификация и эскалация — TASK-031, TASK-032.
- Кэширование финальных ответов навыков/цепочек и медиа — вне этой задачи.
- UI управления кэшем — TASK-061 (здесь только интерфейс очистки/статистики).

## Контракты и интерфейсы

- `ISemanticCache` (семантика по TASK-002):
  - `Task<RouteResult?> TryGetAsync(float[] embedding, CancellationToken ct)`
  - `Task PutAsync(float[] embedding, RouteResult result, CancellationToken ct)`
  - `Task ClearAsync(CancellationToken ct)`, `Task<CacheStats> GetStatsAsync(CancellationToken ct)`
- Реализация опирается на `IEmbeddingStore` (TASK-012): векторный поиск по отдельной таблице/коллекции кэша, не смешиваясь с эталонами intent-ов.
- Конфигурация (TASK-003): порог близости, TTL, максимум записей, включение/выключение кэша.
- `RouteResult` из кэша обязан сохранять исходные intent и параметры; динамические параметры (например, время/дата из текста) кэширующий ярус обязан перепроверять — ограничение фиксируется в документации интерфейса.

## Результаты

- Реализация семантического кэша поверх pgvector (проект — к созданию).
- Конфигурация по умолчанию и очистка по TTL/объёму.
- Unit-тесты политик на фейковом хранилище; component-тест поиска на тестовом pgvector.

## Критерии приёмки

- Повторный близкий запрос возвращает кэшированный `Matched` без вызова классификации (проверяется фейками в TASK-031/032 и собственными тестами).
- Запрос ниже порога близости возвращает промах (`null`).
- `BudgetDenied`, `Failed` и низкоуверенные результаты не записываются.
- Записи с истёкшим TTL и записи другой версии модели не возвращаются при чтении.
- При выключенном в конфигурации кэше `TryGetAsync` всегда промах, `PutAsync` — no-op.
- Превышение максимума записей вытесняет старейшие; размер таблицы ограничен.

## Тестирование

- Уровень: unit + component.
- Как: unit — фейковое векторное хранилище с предзаданными векторами, фейковые часы для TTL, тесты политик записи/версионирования; component — поиск ближайших на тестовом PostgreSQL+pgvector (контейнер/тестовая БД TASK-010), если недоступен — фейк с честной косинусной близостью. Сквозная проверка «кэш экономит LLM-вызов» — в TASK-092, здесь только контрактные тесты.
