# TASK-033 — TokenBudgetGovernor

## Цель

Централизованно ограничивать расходы на LLM: дневной денежный бюджет, лимиты токенов и числа ходов отдельно для облачных и локальных моделей, с учётом фактического использования.

## Контекст

- CyberPipe — персональный ассистент одного владельца (Owner); бюджет защищает от случайных трат на облачные модели и от зацикливания локальных.
- Значения по умолчанию (все конфигурируемы через TASK-003): $0.50/день, 4000 токенов на облачный ход / 12000 на локальный (трактовка лимитов фиксируется в конфигурации), до 3 облачных и 5 локальных ходов на запрос/цепочку.
- Цены моделей берутся из каталогов моделей (TASK-080) по идентификатору модели; локальные модели имеют нулевую денежную стоимость, но учитываются по токенам/ходам.
- Счётчики переживают перезапуск сервиса: хранятся в PostgreSQL (схема — TASK-011). SLO — целевые ориентиры, не ворота.

## Объём работ

- Реализация governor: авторизация вызова по оценке токенов/стоимости, учёт фактического usage, сброс дневных счётчиков по границе суток (локальная TZ владельца из конфигурации).
- Раздельные счётчики: облако/локально; токены входа/выхода; число ходов в рамках одного запроса (контекст запроса передаётся вызывающим).
- Оценка стоимости: `estimatedCost = tokensIn*priceIn + tokensOut*priceOut` по каталогу цен (интерфейс/конфигурация; при отсутствии цены облачной модели — отказ или консервативная оценка по настройке).
- Потокобезопасность: атомарное «проверить-и-зарезервировать» при параллельных запросах; резервирование корректируется фактическим usage.
- API диагностики: текущие остатки бюджета/счётчиков для UI и CLI (только чтение).
- Логирование отказов и приближения к лимитам (TASK-004).

## Вне рамок

- Сами LLM-вызовы — TASK-032; governor только разрешает/учитывает.
- Каталоги моделей и цены как данные — TASK-080; здесь только потребление.
- Отображение бюджета в UI — TASK-061, TASK-062.
- Миграции схемы — TASK-011; здесь только использование таблиц/репозиториев по контрактам.

## Контракты и интерфейсы

- `ITokenBudgetGovernor` (семантика по TASK-002):
  - `Task<BudgetDecision> TryAuthorizeAsync(BudgetRequest request, CancellationToken ct)` — класс модели (облако/локально), оценка токенов, контекст запроса.
  - `Task RecordUsageAsync(UsageRecord record, CancellationToken ct)` — фактические токены, модель, стоимость.
  - `Task<BudgetSnapshot> GetSnapshotAsync(CancellationToken ct)` — остатки по всем лимитам.
- `BudgetDecision`: разрешено/запрещено + причина запрета (`DailyBudgetExceeded`, `TokenLimitExceeded`, `TurnLimitExceeded`, `UnknownModelPrice`).
- Конфигурация лимитов — секция из TASK-003 со значениями по умолчанию выше.
- Хранение счётчиков — через репозитории TASK-013 либо собственную таблицу по схеме TASK-011; интерфейс governor от способа хранения не зависит.

## Результаты

- Реализация governor в проекте роутера или отдельном проекте (к созданию).
- Таблица/записи учёта использования в PostgreSQL по схеме TASK-011.
- Unit-тесты лимитов, сброса суток, конкурентных авторизаций на in-memory фейке хранилища.

## Критерии приёмки

- Вызов сверх дневного бюджета запрещается с причиной `DailyBudgetExceeded`; в пределах — разрешается.
- Лимиты ходов: 4-й облачный ход в одном запросе запрещён при настройках по умолчанию; локальный лимит независим от облачного.
- После границы суток счётчики обнуляются без перезапуска (тест с фейковыми часами).
- Параллельные авторизации не позволяют суммарно превысить бюджет (тест конкурентности).
- `RecordUsageAsync` корректирует резерв фактическими значениями; snapshot отражает остатки.
- Изменение лимитов в конфигурации применяется без изменения кода.

## Тестирование

- Уровень: unit (+ integration при готовности PostgreSQL).
- Как: фейковое хранилище счётчиков и фейковые часы (`TimeProvider`); табличные тесты границ (ровно лимит / лимит+1); конкурентный тест (N параллельных авторизаций). Integration с реальным PostgreSQL — опционально тегом, на тестовой БД TASK-010/011; по умолчанию моки/фейки.
