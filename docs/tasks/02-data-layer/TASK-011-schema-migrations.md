# TASK-011 — Схема базы данных и миграции

## Цель

Создать версионируемую, идемпотентную схему единственной PostgreSQL CyberPipe и механизм миграций вверх/вниз, применимый при старте Service и повторяемый без потери данных.

## Контекст

- Одна PostgreSQL + pgvector на всё приложение (DECISIONS.md, 17-adr-mvp.md OVERRIDE); подключение и проверка расширений — TASK-010.
- В этой же базе позже размещаются таблицы Quartz.NET (TASK-045) и контрольные точки выполнения цепочек Trigger→Skill→Script→Delivery (TASK-044): схема резервирует для них отдельные схемы/префиксы, но не создаёт их здесь.
- Владельца данных разграничивает только роль Owner; Guest удалён — отдельных таблиц/прав для гостя не проектируется.
- Код отсутствует (`CyberPipe.slnx` пуст); проекты и SQL-файлы помечены «к созданию».

## Объём работ

- Каталог миграций `src/CyberPipe.Data/Migrations` (к созданию): последовательно нумерованные миграции `NNNN_<slug>.sql` (вверх) и парные откаты там, где откат безопасен; таблица истории `schema_migrations(version, applied_at, checksum)`.
- Базовая схема (минимальный набор, без бизнес-логики): `embeddings` (метаданные + вектор, детали — TASK-012), `semantic_cache`, `chains`/`chain_runs`/`chain_checkpoints` (только структура под TASK-044), `approvals` (под TASK-046), `token_budget_ledger` (под TASK-033), `kv_settings`, `audit_log`. Точные колонки фиксируются в первой миграции и меняются только новыми миграциями.
- `ISchemaMigrator` / `SchemaMigrator` (к созданию): применение в транзакции на миграцию, проверка контрольных сумм уже применённых миграций, блокировка конкурентного запуска (advisory lock PostgreSQL), режим `ValidateOnly`.
- Отдельные SQL-схемы/роли: `app` (приложение), `quartz` (зарезервирована под TASK-045, создаётся пустой или документируется как создаваемая TASK-045 — выбрать одно и зафиксировать в миграции).
- Индексы по внешним ключам и полям поиска, `created_at/updated_at` по умолчанию, запрет `NULL` там, где домен требует значения; ограничения уникальности для идемпотентных ключей цепочек и кэша.
- Seed только технический (версия схемы, системные настройки по умолчанию без секретов); пользовательские данные не сидируются.

## Вне рамок

## Контракты и интерфейсы

- `ISchemaMigrator.MigrateAsync(CancellationToken) -> MigrationReport` и `ValidateAsync(CancellationToken) -> IReadOnlyList<string>` (расхождения) — к созданию в `src/CyberPipe.Data` (к созданию).
- `MigrationReport { AppliedVersions, SkippedVersions, CurrentVersion }`; ошибка контрольной суммы — `SchemaChecksumMismatchException(version)`, конкурентный запуск — ожидание/понятная ошибка, не частичное применение.
- Соглашение: миграции только аддитивные для уже выпущенных версий; переименование/удаление — через expand-contract (новая колонка → перенос → удаление отдельной поздней миграцией).
- Имена объектов: `snake_case`, префикс схем `app`/`quartz`; каждая таблица с вектором ссылается на размерность из TASK-012, а не задаёт её здесь повторно.

## Результаты

- Из пустой базы одной командой/вызовом поднимается полная базовая схема; повторный вызов ничего не меняет.
- Откат последней миграции (где объявлен) и повторное применение проходят на тестовой базе.
- `ValidateOnly` обнаруживает изменённую применённую миграцию по контрольной сумме.

## Критерии приёмки

- [ ] Пустая база → `MigrateAsync` → все таблицы, индексы и `schema_migrations` созданы; второй вызов возвращает пустой `AppliedVersions`.
- [ ] Изменение файла уже применённой миграции приводит к `SchemaChecksumMismatchException` с номером версии.
- [ ] Два параллельных `MigrateAsync` не дают частичной схемы и не падают с дублями объектов (advisory lock).
- [ ] Откат последней обратимой миграции и повторное применение завершаются без потери строк, внесённых между ними в необращаемые таблицы (проверяется тестом).
- [ ] В миграциях нет секретов, паролей и пользовательских данных; Quartz-таблиц здесь нет, кроме явно зафиксированной пустой схемы/резерва.

## Тестирование

- Уровень: integration (основной) + unit для парсинга/порядка миграций.
- Integration: Testcontainers PostgreSQL + pgvector — пустая база, повторное применение, конкурентный запуск, checksum-mismatch, откат/повтор.
- Unit: порядок версий, обнаружение пропусков нумерации, отклонение миграции без пары отката, помеченной как обратимая.
- Как: фейковая файловая система/встроенные ресурсы миграций для unit; реальная БД только в integration с категорией `Integration`.
