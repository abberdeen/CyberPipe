# TASK-013 — Репозитории и доступ к данным

## Цель

Дать остальным подсистемам типизированный, транзакционный доступ к PostgreSQL через репозитории поверх схемы TASK-011 и хранилища TASK-012 — без SQL в вызывающем коде и без второй базы.

## Контекст

- Схема и миграции — TASK-011; векторное хранилище — TASK-012; подключение — TASK-010; контракты DTO — TASK-002.
- Потребители: исполнитель цепочек и контрольные точки (TASK-044), HITL-одобрения (TASK-046), TokenBudgetGovernor (TASK-033), семантический кэш (TASK-034), персональные навыки и «второй мозг» (TASK-051/TASK-053), аудит безопасности (TASK-070–TASK-073). Здесь нет их бизнес-логики — только чтение/запись и транзакции.
- Только роль Owner; Guest удалён — фильтрации «по гостю» и отдельных прав не проектируется.
- Код отсутствует (`CyberPipe.slnx` пуст); проекты помечены «к созданию».

## Объём работ

- Проект `src/CyberPipe.Data` (к созданию): репозитории по агрегатам схемы TASK-011 — как минимум `IChainRepository`, `ICheckpointRepository`, `IApprovalRepository`, `ITokenBudgetRepository`, `IKeyValueSettingsRepository`, `IAuditLogRepository`; векторные операции не дублируются, а делегируются `IEmbeddingStore` (TASK-012).
- `IUnitOfWork` / транзакционная граница (к созданию): `BeginAsync`, `CommitAsync`, `RollbackAsync`, передача одного соединения/транзакции нескольким репозиториям; автоматический откат при исключении и при отмене по `CancellationToken`.
- Правила доступа: параметризованные запросы только (Npgsql параметры), запрет конкатенации SQL из пользовательского ввода; пагинация `Offset/Limit` с обязательной сортировкой; оптимистичная конкуренция через `row_version`/`updated_at` там, где запись обновляется из нескольких мест (одобрения, контрольные точки).
- Маппинг строк в DTO из TASK-002 без утечки типов Npgsql/pgvector в публичные контракты; `jsonb`-метаданные — через `System.Text.Json` с явными опциями.
- Наблюдаемость: логирование медленных запросов (порог конфигурируем, TASK-003/TASK-004) без значений параметров-секретов; счётчики выполненных/откаченных транзакций для диагностики Service.

## Вне рамок

- Бизнес-правила цепочек, одобрений, бюджета и кэша — TASK-044/TASK-046/TASK-033/TASK-034 (репозитории только хранят и отдают данные).
- Схема и миграции — TASK-011; векторный поиск — TASK-012.
- ORM-миграции и автогенерация схемы из моделей; кэширование в памяти поверх репозиториев.
- Доступ из Desktop/UI напрямую к БД: UI общается со Service, репозитории живут на стороне Service/Brainstem.

## Зависимости

- TASK-002
- TASK-011
- TASK-012

## Контракты и интерфейсы

- Интерфейсы репозиториев (к созданию в `src/CyberPipe.Data`, к созданию; DTO — из TASK-002): методы `GetAsync(id)`, `ListAsync(query с пагинацией)`, `AddAsync`, `UpdateAsync`, `DeleteAsync` по агрегату; отсутствие записи — `null` для `Get`, `false` для `Delete`, без исключений на «не найдено».
- `IUnitOfWorkFactory.CreateAsync(CancellationToken) -> IUnitOfWork`; репозитории получают соединение только из активного unit-of-work или фабрики подключений TASK-010.
- Конкурентное обновление устаревшей версии — `OptimisticConcurrencyException(aggregate, id)`; нарушение уникального идемпотентного ключа — возврат существующей записи или явный результат `AlreadyExists`, по контракту конкретного репозитория (зафиксировать в XML-документации метода).
- Все методы принимают `CancellationToken`; транзакция не переживает отмену токена.

## Результаты

- Каждый агрегат схемы TASK-011 доступен через типизированный репозиторий с тестами CRUD и пагинации.
- Мульти-репозиторная операция в одном unit-of-work либо фиксируется целиком, либо откатывается целиком.
- В публичных контрактах нет типов Npgsql; SQL приложения сосредоточен в `src/CyberPipe.Data` (к созданию).

## Критерии приёмки

- [ ] CRUD каждого репозитория проходит на реальной схеме TASK-011; `Get` отсутствующей записи возвращает `null`, повторный `Delete` — `false`.
- [ ] Операция из двух репозиториев в одном unit-of-work при исключении после первой записи оставляет базу без обеих записей (тест отката).
- [ ] Обновление устаревшей `row_version` даёт `OptimisticConcurrencyException`, а не молчаливую перезапись.
- [ ] Пагинация без сортировки невозможна по контракту (сортировка задана по умолчанию); страницы не пересекаются и не пропускают строки на стабильном наборе.
- [ ] Поиск по коду: SQL-конкатенация пользовательского ввода отсутствует; параметры-секреты не попадают в логи медленных запросов.

## Тестирование

- Уровень: integration (основной) + unit для маппинга и валидации аргументов.
- Integration: Testcontainers PostgreSQL + pgvector со схемой TASK-011 — CRUD, транзакционный откат, оптимистичная конкуренция, пагинация, делегирование векторных операций фейковому/реальному TASK-012.
- Unit/contract: потребители выше по стеку тестируются на фейках этих интерфейсов (отмечается в их задачах); здесь фейки используются только для проверки маппинга DTO.
- Как: категория `Integration` для тестов с БД; unit-тесты маппинга запускаются без Docker.
