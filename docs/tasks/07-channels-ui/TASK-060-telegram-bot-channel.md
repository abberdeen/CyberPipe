# TASK-060 — Telegram-бот: первый канал связи

## Цель

Подключить Telegram как первый канал CyberPipe: бот принимает сообщения Owner, превращает их в chat-триггеры цепочек и входящие сообщения роутера, доставляет ответы и HITL-запросы обратно в Telegram.

## Контекст

- Telegram — первый канал, но не единственный (Q4, Q19): Avalonia (TASK-061) и CLI (TASK-062) развиваются параллельно; логика канала не должна становиться общей логикой системы.
- Канал живёт внутри Service (TASK-020), а не в Desktop: закрытие Desktop бота не останавливает.
- Только Owner (Q18): сообщения от любых других пользователей игнорируются; проверка владельца и whitelist — TASK-073, здесь канал лишь передаёт идентификатор отправителя в контракт проверки и применяет её вердикт.
- Обмен с ядром — только через собственные абстракции сообщений TASK-002 с заменяемым транспортом; библиотека Telegram-бота не протекает в контракты ядра.
- HITL-подтверждения via Telegram — требование ADR: механизм одобрений — TASK-046, здесь только кнопки и передача решения.

## Объём работ

1. Проект канала (to-be-created, например `src/CyberPipe.Channels.Telegram/`): хостинг бота как `IHostedService` внутри Service — long polling (webhook не требуется для локального ассистента; режим выбирается конфигурацией TASK-003).
2. Приём: текстовые сообщения, голосовые (передача аудио дальше как вложение DTO TASK-002; распознавание — TASK-052, здесь не делается), документы/фото как вложения с сохранением метаданных.
3. Маппинг в контракты TASK-002: входящее сообщение -> `IncomingMessage` (канал Telegram, Telegram user id, текст/вложение, время) -> публикация через абстракцию сообщений; текст также создаёт chat-триггер цепочки.
4. Отправка: исходящие сообщения Delivery и ответы роутера -> Telegram (текст, разбивка длинных сообщений по лимиту Telegram, вложения, inline-кнопки действий).
5. HITL: рендер запроса подтверждения из TASK-046 inline-кнопками «Одобрить / Отклонить / Изменить» (Edit — запрос уточняющего текста следующим сообщением); callback возвращает решение Owner в TASK-046; просроченные кнопки отвечают «решение уже не требуется».
6. Команды бота: `/start`, `/status` (состояние Service и бюджет из контрактов), `/stop` (прервать текущую задачу); остальные команды не изобретаются — текст уходит в роутер Tier 0–3.
7. Устойчивость: повторная доставка апдейтов не дублирует обработку (идемпотентность по `update_id`), переподключение при сетевых сбоях с backoff, секреты (токен бота) — только через TASK-003, не в логах.

## Вне рамок

- Роутер Tier 0–3 (TASK-030..TASK-034), исполнение цепочек (TASK-044), механизм HITL и тайм-ауты одобрений (TASK-046).
- Проверка Owner и whitelist (TASK-073) — здесь только вызов её контракта.
- Распознавание голоса (TASK-052), эвристическая безопасность контента/аудио (TASK-071).
- Групповые чаты, публичный доступ, несколько ботов/аккаунтов, Telegram Mini Apps.

## Контракты и интерфейсы

- Потребляет из TASK-002: DTO входящего/исходящего сообщения канала, запрос/результат HITL-подтверждения, абстракцию публикации сообщений, `ChannelKind.Telegram`.
- Вводит только внутренний интерфейс адаптера (to-be-created): `ITelegramBotClientAdapter` (отправка/приём поверх библиотеки бота) — нужен для фейков в тестах; публичные контракты ядра не меняет.
- Идентификатор отправителя передаётся как есть (Telegram user id, `long`); решение «свой/чужой» принимает TASK-073, а не канал.

## Результаты

- Проект Telegram-канала (to-be-created), регистрируемый в Service одной DI-регистрацией.
- Бот отвечает Owner в личке, доставляет Delivery и HITL-кнопки, переживает рестарт Service без потери необработанных апдейтов сверх гарантий Telegram API.

## Критерии приёмки

- Сообщение Owner боту доходит до фейкового роутера как `IncomingMessage` с каналом Telegram; ответ фейкового роутера приходит обратно в тот же чат.
- Сообщение от не-Owner (фейковый whitelist отклоняет) не попадает в роутер; бот не раскрывает содержимое системы в ответе.
- HITL: нажатие «Одобрить»/«Отклонить» возвращает соответствующее решение в фейковый TASK-046; повторное нажатие после решения не меняет исход.
- Дублирующий `update_id` обрабатывается один раз.
- Длинный ответ (> лимита Telegram) доставляется несколькими сообщениями без потери и перемешивания порядка.
- Токен бота отсутствует в логах и в тексте ошибок пользователю.

## Тестирование

- Уровень: unit + component.
- Как: unit — маппинг апдейтов Telegram <-> DTO TASK-002, разбивка длинных сообщений, идемпотентность; component — канал целиком на `FakeTelegramBotClientAdapter` и фейковых роутере/HITL/whitelist из контрактов TASK-002/TASK-073. Реальный Telegram в автотестах не используется; ручная проверка с реальным ботом — по чек-листу приёмки на Windows.
