# TASK-063 — Мастер первого запуска (First-Run Setup Wizard)

## Цель

При первом запуске провести владельца по обязательной настройке CyberPipe: подключение к PostgreSQL, подтверждение владельца (Owner), предложение стандартного эмбеддинга для Tier 1 и подключение первого канала — так, чтобы после мастера система отвечала хотя бы в одном канале.

## Контекст

- Всё хранится в одной PostgreSQL + pgvector (Q2, Q21): если приложение не может подключиться к БД, оно просит владельца восстановить подключение и спрашивает пароль от БД, а не создаёт локальные данные.
- Модели не встроены, включая эмбеддинг (Q15): при первой установке мастер предлагает стандартную мультиязычную модель `multilingual-e5-small` для Tier 1; остальные модели владелец выбирает позже. Установка/настройка локальных моделей (например Qwen3 через Ollama) — инструмент TASK-081, каталоги 15 локальных + 8 облачных JSON — TASK-080; мастер только вызывает их контракты и в автотестах работает на фейках, поэтому TASK-080/TASK-081 в зависимости не входят.
- Только Owner (Q18): мастер фиксирует владельца (Telegram id и/или локальный владелец Desktop/CLI); шагов и веток под Guest нет.
- Мастер живёт в Desktop (TASK-061 как оболочка) и доступен из CLI одной командой; шаги и их логика одни и те же, рендерят их TASK-061/TASK-062.
- Признак «первый запуск» и все введённые данные хранятся в PostgreSQL через TASK-011/TASK-013-контракты; локального флага «настроено» на диске как источника истины нет.

## Объём работ

1. Сценарий мастера (to-be-created, например `src/CyberPipe.Setup/` — логика шагов без UI): последовательные шаги с возвратом назад, прерыванием и возобновлением с места остановки при повторном запуске.
2. Шаг «База данных»: проверка подключения к PostgreSQL (TASK-010), при неудаче — форма хост/порт/база/пользователь и запрос пароля у владельца, повторная проверка, применение миграций через контракт TASK-011; без успешной БД дальше мастер не идёт.
3. Шаг «Владелец»: фиксация Owner — Telegram user id (подсказка, как узнать свой id через бота) и/или подтверждение локального владельца; запись через репозитории контрактов, проверка TASK-073 потребляется как интерфейс-фейк до её готовности.
4. Шаг «Эмбеддинг Tier 1»: предложение установить `multilingual-e5-small` (установка — вызов контракта TASK-081, каталог — TASK-080); варианты «установить сейчас» / «пропустить» с честным предупреждением, что Tier 1 без эмбеддинга не работает и маршрутизация уйдёт в Tier 2/3; повторное предложение при следующем запуске, если пропущено.
5. Шаг «Модели по ярусам» (необязательный): показ текущих назначений Tier 2/Tier 3 из каталогов как DTO, выбор можно отложить; бюджет по умолчанию $0.50/день, 4000/12000 токенов, 3 облачных / 5 локальных ходов показывается и может быть изменён (запись конфигурации — TASK-003, применение лимитов — TASK-033).
6. Шаг «Первый канал»: ввод токена Telegram-бота с проверкой через контракт канала TASK-060 как интерфейс-фейк, либо выбор «начать с Desktop/CLI»; мастер не завершается успехом, пока не настроен хотя бы один канал.
7. Завершение: сводка сделанного, запись признака завершённой настройки в PostgreSQL, запуск проверки «служба отвечает + тестовое сообщение в выбранный канал» на контрактах, отчёт владельцу о результате.

## Вне рамок

- Установка PostgreSQL и создание самой БД/пользователя на машине (TASK-010 — подключение и bootstrap; мастер только спрашивает параметры и пароль).
- Реализация установки моделей и Ollama (TASK-081), содержимое каталогов (TASK-080), советник по железу (TASK-082).
- Проверка Owner/whitelist как механизм (TASK-073), сам Telegram-канал (TASK-060), экраны Desktop/CLI сверх хостинга шагов (TASK-061, TASK-062).
- Миграции существующих установок, импорт данных, восстановление из бэкапа.

## Контракты и интерфейсы

- Потребляет из TASK-002: DTO конфигурации каналов, назначений моделей по ярусам (`TierModelAssignment`), статуса бюджета, `Result<T>`/`ErrorDto`.
- Вводит (to-be-created) состояние мастера как DTO для хранения в PostgreSQL: шаг, введённые не-секретные параметры, признак завершения; секреты (пароль БД, токен бота) в это состояние не пишутся — они уходят только в хранилище секретов TASK-003.
- Вызовы TASK-080/TASK-081/TASK-060/TASK-073 — только через их интерфейсы из TASK-002/профильных контрактов, в тестах — фейки; мастер не ссылается на их реализации.

## Результаты

- Библиотека шагов мастера (to-be-created), одинаково используемая Desktop и CLI.
- После прохождения мастера: БД подключена и мигрирована, Owner зафиксирован, хотя бы один канал отвечает на тестовое сообщение; состояние мастера в PostgreSQL позволяет возобновить прерванную настройку.

## Критерии приёмки

- Недоступная БД: мастер останавливается на шаге БД, спрашивает параметры и пароль, при неверном пароле показывает ошибку и не создаёт локальных данных.
- Прерывание мастера на любом шаге и повторный запуск продолжают с незавершённого шага, завершённые шаги не спрашиваются заново.
- Пропуск эмбеддинга: мастер завершается с явным предупреждением про Tier 1 и предлагает установку при следующем запуске; установка — фейковый TASK-081 получает именно `multilingual-e5-small`.
- Нельзя завершить мастер без Owner и без хотя бы одного канала; веток Guest в шагах и состоянии нет.
- Пароль БД и токен бота отсутствуют в состоянии мастера, логах и сводке завершения.
- Повторный запуск при завершённой настройке мастер не показывает (признак читается из PostgreSQL, а не с диска).

## Тестирование

- Уровень: unit + component.
- Как: unit — переходы шагов, валидация полей, возобновление по сохранённому состоянию; component — мастер целиком на фейках подключения БД/миграций (контракты TASK-010/TASK-011), каталогов, установщика моделей, канала и проверки Owner. Реальные PostgreSQL и Telegram в автотестах не нужны; интеграционная проверка с реальной БД — в TASK-091/TASK-093, ручная на Windows — по чек-листу приёмки.
