# TASK-062 — CLI/TUI клиент

## Цель

Дать владельцу полноценный доступ к CyberPipe из терминала: отправка сообщений ассистенту, запуск цепочек, статус службы и бюджета, HITL-решения и просмотр логов — параллельно с Telegram и Avalonia, а не вместо них.

## Контекст

- Telegram, Avalonia и CLI — три параллельных канала без ограничений «только для MVP» (Q19). CLI не является отладочной заглушкой: сценарии ниже — поддерживаемый продукт.
- CLI — отдельный клиент Service, а не режим службы: работает при закрытом Desktop, службу сам не хостит.
- Только Owner: CLI работает локально от имени владельца; удалённого доступа и ролей/Guest нет.
- Весь обмен — через контракты TASK-002 (`ChannelKind.Cli`) и управление службой через контракт TASK-021 как интерфейс; в тестах он подменяется фейком, поэтому TASK-021 в зависимости не входит.

## Объём работ

1. Проект CLI (to-be-created, например `src/CyberPipe.Cli/`): консольное приложение .NET 10, точка входа `cyberpipe`, кроссплатформенные бинарники под те же ОС, что и Desktop.
2. Режимы вызова:
   - `cyberpipe ask "<текст>"` — одно сообщение роутеру, ответ в stdout, код выхода отражает успех/ошибку;
   - `cyberpipe chat` — интерактивный TUI-чат: история, многострочный ввод, прерывание текущей задачи (Ctrl+C не убивает задачу на службе без подтверждения), выход по команде;
   - `cyberpipe chain list|runs|run <id>` — список цепочек, запуски и ручной запуск function call (определения — TASK-040, исполнение — TASK-044, здесь только вызовы контрактов);
   - `cyberpipe service status|start|stop|restart` — через `IServiceControl` (контракт TASK-021);
   - `cyberpipe budget` — статус токен-бюджета из DTO TASK-033 (по умолчанию $0.50/день, 4000/12000 токенов, 3/5 ходов — значения показывает служба, CLI их не считает);
   - `cyberpipe approve|reject <id>` — HITL-решение по ожидающему запросу (механизм — TASK-046);
   - `cyberpipe logs [-f]` — просмотр диагностического лога (источник — TASK-004).
3. Вывод: человекочитаемый по умолчанию и `--json` для скриптов (стабильная схема = DTO контрактов TASK-002); ошибки — в stderr, ненулевой код выхода, без стектрейсов в обычном режиме (`--verbose` показывает детали).
4. Поведение при недоступной службе: понятная ошибка «Service недоступна» с подсказкой `cyberpipe service start`, код выхода отдельный для «служба недоступна» и «команда отклонена».
5. Конфигурация CLI (адрес/канал подключения к Service) — через TASK-003; секретов CLI не хранит и не запрашивает, кроме передачи пароля БД в сценарии мастера (TASK-063) при его вызове.

## Вне рамок

- Собственный протокол к Service сверх контрактов TASK-002/TASK-021 и транспортные детали (выбор — TASK-090).
- Реализация роутера, цепочек, HITL, бюджета, управления службой — только вызовы контрактов.
- Автодополнение для оболочек, плагины, скриптовый язык поверх CLI, удалённый (сетевой) доступ.

## Контракты и интерфейсы

- Потребляет из TASK-002: DTO сообщений канала (`ChannelKind.Cli`), цепочек/запусков, статуса бюджета, HITL-запроса/решения, `Result<T>` и `ErrorDto` (код ошибки -> код выхода CLI: таблица маппинга фиксируется в коде CLI и покрыта тестами).
- Управление службой — через интерфейс `IServiceControl` контракта TASK-021, потребляемый как интерфейс без зависимости от его реализации.
- `--json` сериализует только DTO контрактов; собственных публичных DTO CLI не вводит.

## Результаты

- Проект CLI (to-be-created) с командами из «Объёма работ», человекочитаемым и `--json` выводом.
- CLI работает при закрытом Desktop; при остановленной службе даёт честную ошибку, а не зависание.

## Критерии приёмки

- `ask` на фейковом роутере печатает ответ и возвращает код 0; ошибка роутера — ненулевой код и сообщение в stderr.
- `chat`: два обмена подряд сохраняют контекст сессии; прерывание задачи в TUI не завершает процесс CLI.
- `service status` на фейковом `IServiceControl` показывает состояние; при недоступной службе — отдельный код выхода и подсказка запуска.
- `chain run <id>` запускает фейковую цепочку и показывает итог Delivery; несуществующий id — понятная ошибка.
- `approve <id>` на фейковом TASK-046 фиксирует решение Owner; повторное решение по тому же id отклоняется.
- `--json` для `budget` и `chain list` проходит проверку схемой DTO контрактов (round-trip десериализация в тесте).

## Тестирование

- Уровень: unit + component.
- Как: unit — парсинг команд, маппинг `ErrorDto` -> коды выхода, форматирование human/JSON; component — CLI целиком на фейках роутера, `IServiceControl`, HITL и цепочек из контрактов TASK-002, процесс службы и БД не нужны. Ручная проверка на Windows — по чек-листу приёмки.
