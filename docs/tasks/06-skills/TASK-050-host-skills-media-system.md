# TASK-050 — Хост-навыки: медиа, система (media/volume/status/timers)

## Цель

Дать ассистенту управляемые голосом/чатом действия над хостом Windows: управление медиа и громкостью, чтение системного статуса и таймеры/будильники, доступные как навыки в цепочках `Trigger -> Skill -> Script -> Delivery`.

## Контекст

- CyberPipe — локальный персональный ассистент, .NET 10, Avalonia для всех ОС, ручное тестирование в фокусе на Windows. Service (Windows-служба, Program Files) и Desktop — раздельно, Desktop управляет Service.
- Навыки вызываются через контракты TASK-002 и маршрутизацию Tier 0–3; DevTools/Git/Build-навыки удалены и здесь не появляются.
- Эвристическая безопасность аудио/контента (не фиксированный Volume Clamp) — отдельная задача TASK-071: навык громкости не реализует clamp 60%/25%, а при необходимости запрашивает оценку риска.

## Объём работ

- Реализовать (to-be-created, напр. `src/CyberPipe.Skills.Host/`) навыки по контрактам TASK-002: `media.play/pause/next/previous`, `volume.get/set/up/down/mute`, `system.status` (CPU/RAM/диск/батарея/время работы), `timer.set/cancel/list`, `alarm.set/cancel/list`.
- Абстракция платформенного бэкенда `IHostMediaController`, `ISystemStatusProvider`, `ITimerService` с Windows-реализацией; не-Windows платформы возвращают явный `NotSupported` результат, а не исключение.
- Таймеры хранятся в памяти Service с опциональной персистентностью через репозитории TASK-011 (если схема это предусматривает); срабатывание публикуется как событие-триггер `chat`/function call по интерфейсам TASK-002.
- Ограничения и подтверждение: резкое изменение громкости и выключение/перезагрузка (если добавляется) — только после HITL-подтверждения (механизм — TASK-046, здесь только флаг `RequiresApproval` в результате навыка).
- Регистрация всех навыков в DI/реестре навыков с именами, описаниями и схемами аргументов для роутера и цепочек.

## Вне рамок

- Эвристическая оценка риска аудио и политика громкости (TASK-071), песочница запуска скриптов (TASK-023), сам механизм HITL (TASK-046), UI управления (TASK-061), планировщик Quartz (TASK-045) — Cron-напоминания идут туда, не в таймеры.

## Контракты и интерфейсы

- Вход/выход — DTO и `ISkill`/`ISkillContext` из TASK-002; ошибки — типизированный результат (`Ok` / `NotSupported` / `ValidationError` / `RequiresApproval`), без непойманных исключений в вызывающий код.
- `ITimerService.SetAsync(TimeSpan, string payload, CancellationToken)` -> `TimerId`; срабатывание — событие через абстракцию сообщений TASK-002 (заменяемый транспорт, без фиксированного брокера).
- Громкость задаётся в диапазоне 0–100; выход за диапазон — `ValidationError`, а не молчаливое усечение.

## Результаты

- Проект навыков (to-be-created) с Windows-бэкендом медиа/статуса/таймеров и реестром навыков.
- Unit-тесты на фейковых бэкендах; запись в реестре видна роутеру/цепочкам.

## Критерии приёмки

- Команды play/pause/next/prev и get/set громкости работают на Windows через фейковый и реальный бэкенд; на не-Windows возвращается `NotSupported`.
- `system.status` возвращает CPU/RAM/диск без падений при недоступности отдельного счётчика (поле = `null` + предупреждение).
- Таймер срабатывает один раз в заданный срок (±1 с в тесте на фейковых часах), `cancel` предотвращает срабатывание, `list` отражает активные таймеры.
- Недопустимые аргументы (громкость вне 0–100, отрицательный таймер) дают `ValidationError`.

## Тестирование

- Уровень: unit + component. Unit — на `FakeMediaController`/`FakeClock`; component — реестр навыков + диспетчер из TASK-002 на моках, без реального аудио-устройства. Ручная проверка на Windows — по чек-листу приёмки.
