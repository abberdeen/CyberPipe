# TASK-053 — Знания: второй мозг (knowledge-second-brain, search/memory)

## Цель

Дать ассистенту семантический поиск по личным знаниям владельца и долговременную память: индексирование заметок/документов, поиск по смыслу и подмешивание релевантного контекста в ответы LLM.

## Контекст

- Одна PostgreSQL + pgvector (TASK-010/TASK-011/TASK-012) хранит и документы, и эмбеддинги; отдельной векторной БД нет.
- Эмбеддинги Tier 1 — стандартная мультиязычная модель `multilingual-e5-small`, предлагаемая при первом запуске (TASK-063); модели не встроены, навык получает `IEmbeddingProvider` через DI и работает на фейковом провайдере в тестах. Та же модель переиспользуется семантическим роутером (TASK-031) и кэшем (TASK-034) — навык не грузит вторую копию модели сам, а пользуется общим провайдером из контрактов TASK-002.
- Только Owner: чужих данных и ролей нет (Guest удалён, авторизация — TASK-073); эгресс-санитизация перед отправкой контекста в облачную LLM — TASK-072, навык лишь помечает контекст как персональный.

## Объём работ

- Реализовать (to-be-created, напр. `src/CyberPipe.Skills.Knowledge/`) навыки по контрактам TASK-002:
  - `knowledge.ingest` — добавить документ/заметку (текст, источник, теги), разбить на чанки (настраиваемый размер/перекрытие), посчитать эмбеддинги, сохранить через хранилище TASK-012;
  - `knowledge.search` — семантический поиск (top-K, порог сходства из конфигурации), опционально гибрид с текстовым поиском;
  - `knowledge.forget` — удалить документ и его чанки/эмбеддинги по ID или источнику;
  - `memory.remember/recall` — короткие факты памяти поверх тех же документов (тип `memory`), с дедупликацией по порогу сходства.
- Провайдер контекста для LLM: `IKnowledgeContextProvider` возвращает не более N фрагментов в пределах настраиваемого бюджета символов/токенов для подмешивания в промпт Tier 2/3; бюджет и N — конфигурация (TASK-003), не константы в коде.
- Переиндексация при смене модели эмбеддингов: версионирование эмбеддингов именем/размерностью модели; несовпадение размерности при поиске — явная ошибка конфигурации, а не пустой результат.
- Источники на каждый фрагмент результата (документ, позиция чанка, score) — для показа пользователю и отладки.

## Вне рамок

- Само хранилище pgvector и схема (TASK-011/TASK-012), ONNX-рантайм эмбеддингов и семантический роутер/кэш (TASK-031/TASK-034), первый запуск и установка модели (TASK-063/TASK-081), санитизация исходящего контекста (TASK-072), CRUD заметок как персональных данных (TASK-051 — здесь только их индексирование поиском).

## Контракты и интерфейсы

- Все операции — через интерфейсы TASK-002/TASK-012 (`IEmbeddingStore`, `IEmbeddingProvider` или эквивалент); SQL и pgvector-запросы живут в TASK-012/013, не в навыке.
- `knowledge.search(Query, TopK, MinScore) -> KnowledgeHit[] { DocumentId, ChunkText, Score, Source }`; пустой результат при низком сходстве — нормальный `Ok` с пустым списком.
- `IKnowledgeContextProvider.GetContextAsync(string query, int tokenBudget, CancellationToken) -> string` с источниками; вызывающий LLM-пайплайн сам решает, включать ли контекст.

## Критерии приёмки

- После `ingest` документа поиск по смыслу (другими словами, без общих ключевых слов фикстуры) находит его в top-3 на фейковых эмбеддингах, спроектированных под фикстуру, и на реальной `multilingual-e5-small` — в ручной/маркированной проверке.
- `forget` удаляет все чанки документа: повторный поиск его не возвращает.
- `memory.recall` не возвращает дубликаты одного факта выше порога дедупликации; `GetContextAsync` не превышает заданный бюджет.
- Смена размерности модели даёт явную ошибку конфигурации при поиске, а не пустую выдачу.

## Тестирование

- Уровень: unit + integration. Unit — чанкинг, дедупликация и бюджет контекста на фейковом `IEmbeddingProvider`; integration — ingest/search/forget против тестовой PostgreSQL + pgvector (Testcontainers). Проверка на реальной ONNX-модели — маркированная категория `Category=RequiresModel`, вне обычного прогона.
