## 6. Технические ограничения

- **Модель исполнения**: процессы Python, роли как LLM-вызовы с общим окружением/пулом сообщений; раунды команды.
- **Детерминизм**: низкий; SOP задаёт порядок этапов, но содержание каждого шага генерирует LLM.
- **Параллелизм**: роли преимущественно последовательны по SOP; массовой параллельности задач нет.
- **Отмена / таймауты**: в проверенных официальных источниках гранулярной отмены шага не детализировано — UNKNOWN.
- **Идемпотентность**: повторный запуск перегенерирует артефакты; идемпотентности шагов нет.
- **Восстановление после сбоя**: промежуточные документы в workspace переживают сбой, автоматического resume пайплайна не заявлено.
- **Версионирование**: документация main помечена unstable при стабильной v0.8 — риск расхождения доков и кода при обновлениях.

## 7. Вердикт и применимость к CyberPipe

**Вердикт**: самый известный фреймворк «AI-компании» с сильным SOP-шаблоном для генерации ПО с нуля, но тяжёлый, дорогой по токенам и слабый в песочнице, итеративной работе с существующим кодом и формальном HITL.

**Применимость к CyberPipe** (локальный персональный ассистент, .NET 10, Telegram+Avalonia, 4-уровневый роутинг Tier0 regex / Tier1 ONNX / Tier2-3 LLM, TokenBudgetGovernor, Netrunner Mini-n8n DAG: SkillNode/NetrunnerScriptNode/ConditionNode/LlmProcessNode/HitlApprovalNode/DeliveryNode, SQLite WAL, Brainstem sandbox process, HITL):

- **Как зависимость — не применим**: Python-стек, нет .NET/Telegram/Avalonia, нет формального DAG с Condition/HitlApproval-узлами.
- **Что заимствовать**: (1) SOP как документированные стандартные процедуры для типовых Netrunner-воркфлоу (шаблоны DAG с ролями LlmProcessNode: аналитик → исполнитель → проверяющий); (2) промежуточные читаемые артефакты между ролями (PRD/дизайн как контракты между узлами) — хорошая практика для схем входов/выходов узлов Netrunner; (3) роль QA как отдельного проверяющего узла после генерации.
- **Предупреждения**: (1) полная «компания» агентов конфликтует с TokenBudgetGovernor — CyberPipe должен запускать мультиролевые сценарии только на Tier3 и с жёстким бюджетом на весь DAG; (2) отсутствие песочницы (#1956) подтверждает приоритет Brainstem sandbox process; (3) нестабильность отдельных LLM-бэкендов (#1859) требует в CyberPipe контрактных тестов провайдеров при смене модели.
- **Итог**: референс по SOP-шаблонам и меж-узловым артефактам, не интеграция.
